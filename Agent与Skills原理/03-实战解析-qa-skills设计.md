> **本文的写法**：不解说 qa-skills，而是**带你把它重新发明一遍**。
> 每一章，你会先遇到一个和 qa-skills 作者当年一模一样的坑，亲手做出一模一样的决策——然后我告诉你：**qa-skills 仓库里对应的那个文件、那条规则，就是你刚做的事**。
> 走完全程，它的 10 个技能、共享库、流水线、证据体系、决策矩阵，每一个目录你都"写过"。再看那个仓库，就像看自己的代码。

## 第一章 第一个技能：先让它能干活

> Success check：你说"帮我测这个功能"，Agent 能产出一份测试用例文件。

### 1.1 造第一个 skill（10 分钟）

```bash
mkdir -p ~/.agents/skills/test-case-writing
```

写 `SKILL.md`（这就是 qa-skills 里最大的那个 skill 的雏形）：

```markdown
---
name: test-case-writing
description: 根据需求文档或代码仓库编写测试用例时使用。凡用户说"帮我测这个功能、
  写一下测试用例、这个需求怎么验证"时都应使用。
---

# 测试用例编写

1. 读取用户提供的需求文档（或让用户指路）。
2. 列出所有功能点，每个功能点写若干条用例，格式：
   - 用例名 [P0/P1/P2]
     - 操作步骤：1. ... 2. ...
     - 预期结果：...
3. 主流程标 P0，异常情况标 P1，极端边界标 P2。
```

测一下：把"优惠券到期自动结束：已发布的券到设定的结束时间后，1 小时内状态自动变为已结束"这句需求发给 Agent。

**预期看到**：产出十几条用例——格式工整、术语专业、看着像那么回事。

### 1.2 然后，看出不对劲（认真看）

拿其中一条，想象自己是**明天入职、对这个项目一无所知**的执行者：

```text
TC-05 到期自动结束验证 [P1]
操作步骤：选择一张即将到期的已发布优惠券，等待到期
预期结果：功能正常
```

三个问号：哪张券？去哪个页面选？"功能正常"怎么判定？等多久算到期？——**你没法开工**。这就是 qa-skills 设计文档里的原话：

> **"AI 写出的用例常常看似专业、实则无法执行——判定模糊、占位符、无判定时限、虚构入口。"**

而且原因被它精准画像了（5 种失败模式，你对号入座看看刚才的产出中了几条）：凭空想象系统（没看过真实页面就在写"进入券工场"）、写给评审者而非执行者、前置不可得、判定不可操作、断言超出验证强度。

### 1.3 你的第一版改法（现在动手）

```markdown
2. 每条用例必须让"没读过需求的新人"能直接开工：
   - 操作步骤写到"进入哪个页面、点哪个按钮、填什么数据"的粒度；
   - 数据写具体值（如"满100减20-测试券"），禁止"测试券"这种占位符；
   - 预期结果可判定：异步行为必须写时限（如"到期后 1 小时内变为已结束，超 1 小时未变判失败"）。
```

改完重测，拿产出再当一次"新人"检查。**好一些了，但还有问题**：Agent 偶尔还是会编——编一个页面上不存在的"批量选择"按钮。为什么？因为它根本没看过这个系统，它在**想象**。

> **对上了**：
> - 你的"新人能直接开工"标准 = qa-skills `core/executability.md` 的**一票否决总纲**（原文："没读过需求、没人讲解的人，拿着文件能直接开工"）；
> - 你的"具体值禁占位符 / 异步判定时限" = 该文件 8 条硬标准中的两条；
> - 它在评测里真的把这条当狠手：**不可执行的用例，覆盖再全也计零分**。
> - "Agent 在想象系统"这个问题，qa-skills 用一整章解决——下一章。

## 第二章 两大灵魂：代码优先 + 证据体系

> Success check：你的 skill 会先要代码、每个结论挂证据；你能背出 E0–E4。

### 2.1 坑：凭空想象 → 解法：代码优先

第一章末尾的"编造按钮"问题，根源是**输入里没有事实**。qa-skills 的解法干脆利落（它的四大支柱第一条，Code-aware）：

> **代码是静态事实的最高来源。** 有代码必读代码，以实现为准，文档降为对照。

改你的 SKILL.md，把"开工第一件事"换成主动要代码：

```markdown
1. 开工先索取被测仓库（仓库地址、被测分支、若有 PR/diff 范围也一并要）。
   用户确认无代码 → 降级纯文档模式，并提示"无法发现文档与实现不一致、无法定位潜在 bug"。
```

重测（给一个真实仓库）。**预期看到**：用例里的入口、字段、默认值都对得上真实代码了——因为它**看过**。

### 2.2 新坑出现：结论没头没尾

读代码后 Agent 变得爱下断言："`expire_job.py` 里有并发竞态，会导致重复结束券。"——真有吗？哪行？它说的还是它猜的？

qa-skills 对此的判断是：**"禁止不加标注直接输出'这里存在 Bug'"——这是证据体系要消灭的幻觉式结论。**

### 2.3 造证据体系（qa-skills 最有辨识度的构件，现在归你）

先想清楚"信什么"的排序，再造一把尺子。你的版本：

```markdown
## 证据标注（每条结论必须挂）

E0 用户陈述 < E1 需求文档 < E2 代码(文件:行) < E3 运行结果 < E4 多来源互证

冲突裁决：
- 代码怎么写的（静态）→ E2 说了算；文档与代码不一致，以代码为准，偏离记入附录并问用户
- 系统实际怎么表现（动态）→ E3 说了算；代码与运行不符，本身就是发现
- 应该是什么行为（意图）→ 用户在澄清环节的答复说了算，后续不得推翻
```

给每条发现套上格式：

```yaml
finding:
  title: 券到期任务存在并发竞态
  evidence: { level: E2, source: "expire_job.py:47" }   # 没有来源 = 不许说
  confidence: medium
  status: hypothesis   # fact/inference/risk/hypothesis/verified 五选一
```

重测。**预期看到**：那个"并发竞态"变成了带 `文件:行` 的 hypothesis——要么能查证，要么显式是猜的。

### 2.4 一个精妙的坑（试试你能不能踩到）

问 Agent："这个券到期功能要多久生效？"用户随口说"应该是实时吧"。Agent 记下了。后来读代码发现是定时任务每小时跑——**它该听谁的？**

qa-skills 的答案藏着一个关键区分：**E0（用户随口说的）是低证据，可以被代码推翻；但用户被正式问过之后的"裁决"不是证据、是决策，不可推翻。** 前者是输入，后者是命令。

> **对上了**：你刚写的整个体系 = `core/evidence.md`（E0–E4、三类裁决、五状态、标注格式——逐条对应）；"以代码为准"在 qa-skills 里有个名字叫**测准声明**；`test-case-writing` 的附录缺陷记录 Cx 格式（现象 + evidence + status）就是你那个 finding 块。它的四大支柱你已造出两个：**Code-aware、Evidence-driven**。

## 第三章 拆家时刻：三层架构与共享库 core/

> Success check：你能说出 L1/L2/L3 各装什么；你的 core/ 诞生了。

### 3.1 刻意养胖

真实需求会长大。往 SKILL.md 里继续加：状态机法怎么用（状态提取→每条边一条用例→非法转换）、边界值法、数据驱动法、权限矩阵法、格式模板、术语表规范、FAQ……加到 100+ 行。

**症状**（跑几次感受一下）：变慢（每次全文进上下文）；变笨（方法 A 和 FAQ 第 3 条打架，随机执行）；关键约束被稀释。这叫**指令过载**。qa-skills 引 Red Hat 实测钉了条红线：**SKILL.md 超 500 行性能退化**——全能型 skill 是反模式。

### 3.2 拆三层（qa-skills 的核心架构，动手）

判断标准一句话：**每次触发都要走的留正文；只在一部分情况才要的搬出去、留显式指路。**

```text
test-case-writing/
├── SKILL.md              # L2 工作流：流程主干（qa-skills 红线 ≤500 行）
│                         #   头部 = L1 触发边界：什么时候用/不用/交给谁
├── references/           # L3 按需加载
└── （方法细则、模板……先记着，马上有去处）
```

SKILL.md 里留的指路长这样（注意措辞，**不是"可选参考"**）：

```markdown
3. 设计方法选择（此时执行 methods/state-machine.md 或对应方法全部步骤）
5. 定稿自检（此时执行 executability.md 全部检查项，不是可选参考）
```

### 3.3 造 core/（你很快会"被迫"做这一步）

预告一下流程：下一章你会拆出第二、第三个技能（策略、需求分析），然后发现——证据规范它们也要用、格式规范它们也要用。**三份拷贝，改一处忘两处。**

解法就是 core/，规则两条（qa-skills 原文）：

1. **至少两个 skill 消费的内容才下沉**（防过早抽象）；
2. **skill 之间禁止互相引用**，共享内容一律走 core/（保证每个 skill 自包含）。

先建好并搬入第一批住户：

```bash
mkdir -p ~/.agents/skills/core/methods ~/.agents/skills/core/scripts
mv ~/.agents/skills/test-case-writing/references/{evidence,executability,case-format}.md ~/.agents/skills/core/
```

给 core 一个"我是依赖不是技能"的声明（qa-skills 原文风格）：

```markdown
---
name: core
description: 本目录是共享知识库（安装依赖单元），不定义工作流、不面向任务触发。
  任何测试任务都不要独立触发我，独立使用无意义。
---
```

注意这个设计的深意：core 的 SKILL.md **存在但从不参与触发竞争**——它只让安装器知道"装任一技能必须连我一起装，否则相对路径断裂"。

> **对上了**：L1/L2/L3 三层 = DESIGN.md 第 3 节"三层架构规范"（含 ≤500 行红线、外移不降级、宁窄而深）；`core/` 及其两条准入门 = DESIGN.md 硬规则第 5 条；你 2.x 写的 evidence/executability/case-format 现在住的位置 = 仓库 `skills/core/` 根下那 10 个文件的其中三个。**CI 强制**（`validate_skills.py`：超 500 行、缺 When NOT to Use、引用不存在文件、跨 skill 引用——直接报错）你现在还体会不到疼，第五章造编排时会回头补。

## 第四章 为什么是 9 个阶段技能：拆分逻辑

> Success check：你能回答"为什么写用例的技能里不该包含定策略"。

### 4.1 踩到"职责越界"的坑

现在你的用例技能已经不错了。但试试这句话："**这个优惠券功能应该怎么测？**"——用户要的不是用例，是**决策**：范围多大、哪些类型测、测多深、优先级怎么排。你的技能硬着头皮答了，产出夹在用例文件里，四不像。

qa-skills 的判断：**写用例之前，先有一道独立的决策工序**。拆！而且往上游再想一步——决策依据从哪来？需求先要**建模**（目标/边界/规则/模糊项）。于是自然长出三个阶段技能：

```bash
cd ~/.agents/skills
cp -r test-case-writing requirement-analysis   # 改造成：需求建模
cp -r test-case-writing test-strategy          # 改造成：风险+策略
```

各自瘦身（把不属于自己的部分删掉）：

| 技能 | 留什么 | 删什么 |
| --- | --- | --- |
| `requirement-analysis` | 输入研读、模糊/矛盾项扫描、澄清提问并落盘 | 所有写用例的内容 |
| `test-strategy` | 风险识别评级、范围/深度/优先级决策 | 用例格式、设计方法 |
| `test-case-writing` | 设计方法、格式、自检 | 需求澄清的细节（消费上游产物即可） |

### 4.2 风险模型：评级必须挂证据（第二章思想的延伸）

test-strategy 的核心产出是 Risk Map。造它时把第二章的证据体系接上——qa-skills 三条铁律：

```markdown
## 风险评级铁律（写入 core/risk-model.md）

1. Risk Score = Impact × Likelihood（各 1–5）→ Critical/High/Medium/Low
2. 没有证据的风险评级视为无效评级（评级字段必须带 evidence）
3. 风险等级（Critical…）与用例优先级（P0/P1/P2）是两套体系，不同名，避免歧义
```

第 3 条是有来历的：同名会让"P0 风险"和"P0 用例"混淆。**领域细节，但设计思想通用：任何会产生歧义的概念对，改名分开。**

### 4.3 下游也长出来了

继续问自己"写完用例之后呢"：谁来挑用例的错（**审查**）？怎么变成能跑的代码（**E2E / API 自动化**）？跑出 Bug 谁来定位根因（**bug-analysis**）？改了代码怎么定回归范围（**regression-testing**）？没有需求文档怎么探索（**exploratory-testing**）？——**9 个阶段技能就此齐了**。每个都复制瘦身，各自一条触发词边界。

> **对上了**：这不是拍脑袋拆的，DESIGN.md 的判断标准是**用户意图粒度**——"帮我测这个需求"（终态）和"帮我审一下这份用例"（单阶段）是不同意图，必须各自由独立技能承接。你第 4.1 步遇到的"四不像"就是证据。风险模型 = `core/risk-model.md`；"评级挂证据"原文即"没有证据的风险评级视为无效评级"。至此四大支柱齐三：**Code-aware / Risk-driven / Evidence-driven**（第四个 Evaluated 在第八章）。

## 第五章 大梁：薄编排 qa + 文件即流水线状态

> Success check：一句话跑通全流水线；中断后新会话能续跑。

### 5.1 触发竞争（多技能必然翻的车）

9 个技能装好后测这句："**帮我测试这个需求**"。症状：`test-case-writing`、`test-strategy`、`requirement-analysis` 的 description 全含"测试"——**都想接**，随机命中或全部加载。qa-skills 原话：**"没有负向约束的触发竞争会让整个体系形同虚设。"**

### 5.2 修法 A：反触发表

每个技能 description 补"不用于 → 交给谁"段（写之前先列对照表）。样例（qa-skills 原文式）：

```markdown
description: 编写可执行的手动测试用例时使用——代码优先……
  不用于：需求建模（requirement-analysis）、测试策略（test-strategy）、
  独立审查（test-case-review）、自动化脚本（automated-e2e-testing/api-testing）。
```

### 5.3 修法 B：造 qa——薄编排（整个框架的"总入口"）

但"帮我测试这个需求"这句**终态意图**仍没人独占——它要串起全部 9 个阶段。造第 10 个技能 `qa`：

```markdown
---
name: qa
description: 端到端测试的唯一入口：用户说"帮我测试这个需求/功能"时，编排
  需求理解→策略→用例→审查→执行→Bug分析→回归→报告的完整流水线。
  只要单阶段产出（如"帮我审一下这份用例"）→ 直接用对应阶段技能，不用本技能。
---

# QA 编排入口（薄）

本 skill 是薄编排：不含任何测试方法与框架知识。它失败的唯一合理原因是
编排错误，不是测试判断错误。

## 流水线（文件即状态）

| # | 阶段 | 调用 | 落盘产物 | 检查点 |
|---|------|------|---------|--------|
| 1 | 需求理解 | requirement-analysis | 需求模型.md | ⏸ 澄清 |
| 2 | 测试策略 | test-strategy | 测试策略.md | ⏸ 预算 |
| 3 | 用例编写 | test-case-writing | 测试用例 markmap + schema | — |
| 4 | 用例审查 | test-case-review | 修订后用例 | — |
| 5 | 执行 | e2e/api/手动 | 代码+运行结果 | ⏸ 执行策略 |
| 6 | Bug 分析 | bug-analysis | Bug 条目 | ⏸ Bug 定性 |
| 7 | 回归验证 | regression-testing | 回归清单.md | — |
| 8 | 报告 | 本 skill | 测试报告.md | — |

（另有可选的**阶段 0**：`exploratory-testing` 旁路先行——文档缺失/系统陌生时先探索。所以仓库自称"9 阶段流水线"。）

## 硬规则

1. 不做裁决：⏸ 环节呈现问题后等用户，不代答
2. 不含领域知识：测试方法全在阶段技能与 core/，本 skill 只做调度
3. 阶段产物消费走文件：传的是产物路径，不是会话转述
4. 状态全在文件：任何会话中断后，凭落盘产物即可续跑
```

三条硬规则里藏着本章后半的主角。**现在做两个实验**：

- **实验一（断点续跑）**：让流水线跑到第 3 阶段，直接关掉会话；新开会话说"继续"。**预期**：qa 先扫 `{项目}/` 下有哪些落盘文件，从最后一个完整阶段之后继续——不重做。**这就是"文件即流水线状态"**：上下文会断、会压缩、会腐烂（第一篇 6.1 的 context rot），磁盘才可靠。
- **实验二（上下文隔离）**：注意 qa 的表格里，每一行只写"调用哪个技能、产物是什么"——它**从不加载**阶段技能的正文。宿主支持子代理时每个阶段在独立上下文里跑，任一时刻活跃指令 ≤1–2 个技能；不支持时退化为顺序会话+文件衔接，正确性不变。

### 5.4 补上 CI 那一脚

人多手杂会破规矩。把第三章欠的账结了——qa-skills 用 `validate_skills.py` 把架构红线变成 CI 强制：**SKILL.md 超 500 行、缺 When NOT to Use、引用不存在的文件、跨 skill 引用、core 文件被 eval 引用——任一命中直接报错，合并不了**。你的最小版：

```python
# validate_skills.py 最小版：查三件事
MAX_LINES = 500
# 1. 每个 SKILL.md ≤ 500 行
# 2. 每个 SKILL.md 必须有 "When NOT to Use"
# 3. 文中反引号引用的相对路径文件必须真实存在
```

> **对上了**：你的 qa/SKILL.md 与仓库 `skills/qa/SKILL.md` 几乎逐段对应（编排会话模型、流水线表、四条硬规则、Common Mistakes 表）；"文件即状态"三重身份（断点续跑/隔离介质/回归追溯数据源）= DESIGN.md 第 6 节；CI 校验 = `scripts/validate_skills.py` 的第 2、3、5 条规则。**反模式警告**也值得抄走：单会话内顺序累加加载全部 SKILL.md（9 个 × 数百行同时在场）。

## 第六章 双轨产物与下游技能：让用例"可流转"

> Success check：你的用例有 markmap（人读）+ schema.yaml（机器读）两副面孔，且后者永远可再生。

### 6.1 新问题：下游技能怎么消费用例？

`regression-testing` 要干的事：代码改了，**哪些用例受影响？** 让模型"读一遍 diff 再读一遍用例猜"——不可靠。它需要的是**结构化映射**：每条用例挂在哪些代码位置（code_refs）、关联哪条风险（risk_ref）。

### 6.2 双轨设计（qa-skills 的巧妙解法）

```markdown
## Schema 双轨原则（写入 SKILL.md）

- 测试用例_markmap.md：给人的交付物 + 唯一人工维护源
- 测试用例.schema.yaml：机器可读层，由 markmap 单向抽取，永远可由 markmap 再生
- markmap 改动后必须重新抽取；不要求人维护两份
```

抽取规则独立成 `core/schema-extraction.md`，并配校验脚本（进 `core/scripts/`）：

```python
# validate_schema.py 最小版
# 1. YAML 合法性  2. TC 编号与 markmap 一致  3. 无占位符残留
```

这样三类消费者各取所需：**测试工程师**读 markmap 开工；**test-case-review** 用 schema 算覆盖分母；**regression-testing** 用 code_refs 做影响面反查。下游技能（review/e2e/api/bug-analysis/regression）此时才真正"有米下锅"——它们消费的都是上游落盘文件。

### 6.3 顺手补一个实招：无 UI 功能怎么办

优惠券到期是后台定时任务，**测试工程师根本无法独立执行**。qa-skills 的判定叫**执行模型判定**：开工先判有无 UI；无 UI 的写成"测试-开发协作清单"（步骤标"请开发执行"，预期标"请开发反馈查库结果"）。把这条加进你的 case-format——它拦住了大量空中楼阁。

> **对上了**：双轨 = DESIGN.md 第 8 节（含那句关键动机："没有它，回归范围选择就只是'让模型读一遍 diff 猜'"）；校验 = `core/scripts/validate_schema.py`；执行模型 = `test-case-writing` 阶段一"受众与执行模型判定（开工必做）"。markmap 渲染：VS Code 装 Markmap 扩展或 `npx markmap-cli`。

## 第七章 王牌：类型决策矩阵（qa-skills 最独特的设计）

> Success check：你的策略产出里，十个类型每轴都有显式决策——含不做的。

### 7.1 它发现了一个惊人的事实

qa-skills 做评测时发现：**未装 skill 的模型制定测试策略，30 次采样零显式类型决策**——输出里"提到"了性能与安全，却从不决定哪些纳入、测多深、哪些明确不测。**提到不等于决策；不可审计的策略等于没有策略。** 盲区不在类型知识，在决策纪律。

### 7.2 造矩阵（你可以先自己试试）

先自己回答："优惠券功能要不要测性能？"——多半会答"看情况"。**"看情况"就是没决策**。现在强制改答法，三选一：**纳入（挂信号）/ 排除（挂理由）/ 移交（挂接收方）**。十轴每轴必答：

```markdown
# core/test-type-matrix.md（你的浓缩版，仓库是完整十轴六字段）

轴 1 性能效率：需求有 SLA/秒杀 → include（挂该信号）；无信号 → exclude
  （必须引用扫描结果："已查无分页全量查询/循环内远程调用等 G 级信号"）
轴 2 业务安全：Web/API 系统一律 standard——硬默认，无 exclude 出口
  （成本极低×价值极高，这是专家的默认直觉）
轴 3 可靠性 / 轴 4 并发 / 轴 5 兼容 / …（十轴，每轴同结构）
```

配套两个机制（弱模型增益的秘密）：

- **G 级信号脚本扫描**：`core/scripts/scan_signals.py` 用 grep 类模式扫代码（如"无分页的全量查询""循环内远程调用"这类模式），产出**预填表**——模型从预填表**修订**而不是从空白生成。同代码必得同信号，这是把"类型视野"从模型能力变成框架能力；
- **排除要双确认**："脚本无命中"单独不构成排除依据（脚本有盲区），须 S 级语义复核——**防脚本盲区被制度化为漏测**。

策略产出 `type_scope`：每轴一行，机械可校验（V1–V5）。实测：最弱模型类型查全率 **0 → 0.88**；需求未提、只存在于代码里的可靠性/契约轴 **0 → 8/9**。

### 7.3 矩阵自己的纪律（细节见人品）

矩阵甚至对自己立规矩：可用性/渗透/SAST 等**不设轴的类型也留痕**——各自写明不设的理由和出路（右移/人工/handoff）。**排除也要留痕，矩阵自身遵守自己的原则。**

> **对上了**：`core/test-type-matrix.md`（完整版按轴独立成节、分轴组加载——300 行不整文件进上下文，渐进披露用到极致）；扫描器 = `core/scripts/scan_signals.py`；六条设计原则（全轴必答/include 挂信号/exclude 挂理由/depth 与 execution 分离/单一真相/弱模型优先）= `docs/decision-layer-design.md` §1.3。域间裁决也有先例：permission（功能域）管授权正确性、业务安全（类型域）管越权防御，同一批越权用例不得双计数。

## 第八章 收官两件套：检查点 + 评测（它最硬核的部分）

> Success check：你有一个黄金集，跑过 On/Off 对照，见过"单次对比是噪声"。

### 8.1 检查点：哪些事模型不许代答

qa-skills 圈了四类：**澄清**（需求模糊项）、**执行策略**（手动/E2E/API）、**Bug 定性**（缺陷还是预期）、**预算裁决**（full 档超预算砍哪个）。共同形态（你第五章的 ⏸ 已埋了雏形）：**呈现提案 → 等用户 → 裁决落盘 → 后续不得推翻**。理由一句话：这些是**人的责任**，Agent 代答等于埋雷。

### 8.2 评测：先造尺子，再谈改进

qa-skills 最反直觉也最值钱的部分——**评测先于扩容建设**。它的方法学里三条最值得抄：

1. **On/Off 对照 + 多采样**：同一模型同任务，开/关 skill 各跑 n=3，比 delta。**真实教训**：单次对比 +28.8pp，多样本复验证实是噪声，实际 +6.2pp；
2. **预注册冻结门**：阈值在验证轮前定死记档，**不因数据改门**；
3. **如实披露反向结果**：API 执行曾出现 74%(无) vs 52%(有) 的反向数字——README 正文照登，后来逐失败归因定案为**评测任务自身缺陷**（状态机断裂），修复后 100% vs 99.2%。**评测失去诚实就失去意义。**

它的北极星指标：**跨模型增益下限（min 不是均值）**——"对单一模型迭代出的提升若不能跨模型复现，视为过拟合而非进步"。

你的 30 分钟最小版：

```text
黄金集（2–3 个带标准答案的任务）：
  任务 1：对 <真实仓库> 写"优惠券到期"用例
    标准要点：主流程/时间双侧边界/无 UI 协作式 —— 可逐条打勾
  任务 2：同仓库出测试策略 —— 十轴每轴有决策 = 每轴 1 分
跑法：移走 skills/ 跑一遍（Off），装回跑三遍（On），逐条打分记波动
```

> **对上了**：四类检查点 = `qa/SKILL.md` 流水线表的 ⏸ 列 + `core/clarify-pattern.md`；评测 = DESIGN.md 第 10 节 + AGENTS.md（北极星、三轨道、迭代纪律："+2pp 级差异一律视为采样噪声"）；四大支柱至此齐四：**Code-aware / Risk-driven / Evidence-driven / Evaluated**。代价也要知道：**token 成本 3.3×**——更好但更贵，README 照登。
