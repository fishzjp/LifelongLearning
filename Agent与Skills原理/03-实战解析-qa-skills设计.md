# 从 0 到 1 设计一套 Skills：动手造一个，再看懂 qa-skills

> **本文是一篇"跟着做"的教程**，不是一篇"读一读"的文章。
> 你将从零开始，亲手把一个 20 行的小技能，一步步养成一套有编排、有共享库、有纪律、有评测的 skill 框架——**过程中每遇到一个真实的坑，就学一个真实的设计**。
> 全程以开源项目 [qa-skills](https://github.com/fishzjp/qa-skills)（生产级测试工程框架）为"大师对照"：你走到哪一步，就看它在这一步是怎么做的。

## 开始之前：你会做出什么、需要什么

**你将做出**（成品先看，学 React 教程的做法）：

```text
report-suite/                  # 你将拥有的技能套件
├── report/                    # 编排入口："帮我整理本周汇报"一句话跑全流程
├── daily-report/              # 日报：从 git + 待办提取当天工作
├── weekly-report/             # 周报：汇总日报 + 本周提交
├── monthly-report/            # 月报：汇总周报 + 提取趋势
├── standup/                   # 站会稿：今天/昨天/阻塞
└── core/                      # 共享知识库：数据来源规范、证据规则、汇报格式
```

用法就是对 Agent 说一句"**帮我整理本周汇报**"——它自动跑数据收集 → 分类归纳 → 证据核对 → 草稿 → 等你裁决 → 定稿。

**你需要**（前置条件，不满足也有替代路径）：

| 需要 | 说明 | 没有怎么办 |
| --- | --- | --- |
| 一个支持 Skills 的 Agent | TRAE / Claude Code / Cursor 均可 | 用任何能读文件的 AI 工具模拟：手动把 SKILL.md 内容贴给它 |
| 一个 git 仓库 | 有提交记录即可，哪个项目都行 | 没有 git 仓库就换数据源（文件夹、备忘录），流程完全一样 |
| 60–90 分钟 | 分六章，每章 10–20 分钟 | 每章独立成段，可分多次做完 |

**你不需要**：懂测试、懂 qa-skills、看过前两篇（需要时本文会给"够用的一句话解释"+ 指回链接）。

**贯穿案例为什么选"工作汇报"**：零领域门槛（人人都懂周报）、数据真实（就在你的 git 里）、而且它会**天然长出**一套 skill 框架需要的所有结构——多技能、编排、共享库、纪律、评测。qa-skills 用的领域是软件测试，结构一模一样。

## 第一章 10 分钟：跑通你的第一个技能

> **本章 Success check**：做完后，你在新会话里说"帮我整理下这周干了啥"，Agent 会用你的格式产出周报——哪怕它还很粗糙。

### 1.1 建 skill（就两个动作）

选一个"走到哪都想用"的位置。用跨工具标准目录 `~/.agents/skills/`（TRAE / Claude Code / Cursor 都认）：

```bash
# 创建技能目录：一个 skill = 一个文件夹 + 一份 SKILL.md
mkdir -p ~/.agents/skills/weekly-report
```

创建 `~/.agents/skills/weekly-report/SKILL.md`，内容如下（**可以直接复制，但建议手敲一遍**——手敲过一次才记得住结构）：

```markdown
---
name: weekly-report
description: 根据本仓库 git 提交历史生成中文工作周报。凡用户提到"周报、weekly report、
  本周总结、这周干了啥、汇报一下这周做了什么"时都应使用。
---

# 周报生成

1. 运行 git log --since="7 days ago" --no-merges --pretty=format:"%ad|%s" --date=format:"%m-%d"
   获取本周提交，按天分组。
2. 把提交整理成三段：完成事项（合并同类项，提炼意图而非罗列）、数据/成果（有数字写数字，
   没有就删掉这节）、下周计划（从提交趋势推断，标注"待确认"）。
3. 每一条"完成事项"后面必须附上它来自的提交日期，禁止编造没有的工作。
```

### 1.2 验证（三步，每步都有"预期看到"）

**验证 1**：重开会话（或在 TRAE 里确认技能已加载），输入 `/weekly-report` 或看技能列表——**预期看到** `weekly-report` 出现在可用技能里。

**验证 2**：说一句故意口语化的话："帮我整理下这周干了啥"——**预期看到** Agent 去跑了 `git log`，而不是凭空编周报。它开始执行命令，就说明触发成功。

**验证 3**：检查产出有没有三段结构、有没有编造——大概率**会发现问题**（格式不守、罗列 commit 不合并、甚至编了两条你没做过的事）。

**发现问题 = 本章的正常结局，不是失败。** 下一章就是修它。

### 1.3 刚才发生了什么（原理，事后揭秘）

- 你写的那个 `---` 包住的头（frontmatter）里，**只有 description 决定这个技能什么时候被翻开**。你把"这周干了啥"这种口语写进去，就是在给触发铺路（模型倾向漏触发，措辞要外向）；
- 正文是写给模型看的操作流程：祈使句、有步骤、有一条反编造护栏；
- 技能没被触发时，只有 name + description 常驻上下文（约 100 token），正文不占地方——这叫**渐进式披露**（详见[第二篇](02-Skills原理.md)第四章）。

> **大师对照 · qa-skills 在这一步怎么做**
> 它每个 SKILL.md 的 description 都是"什么时候用 + 什么时候不用 + 交给谁"三段式，例如写用例技能的 description 明确写着"不用于：需求建模（requirement-analysis）、测试策略（test-strategy）……"。
> **为什么比你的多一段"不用"**：它有 10 个技能，description 重叠会引发触发竞争。你现在只有 1 个，暂时不需要——记住这个伏笔，第四章见。

**Recap**：一个 skill = 文件夹 + SKILL.md；description 管触发、正文管流程；验证要连"口语触发"一起测。

## 第二章 遇到三个坑：质量问题是"设计"的起点

> **本章 Success check**：你能说出你的 skill 现在的三个失败模式，并且学会用一个动作治"编造"这个最危险的失败。

上一章验证 3 发现的问题，正是本章的原材料。真实教程不会假装一次写对——**qa-skills 的设计文档里每个机制旁边都标着它治什么病**，我们现在做同样的事。

### 2.1 坑一：编造（最危险）

模型会往周报里塞"完成 XX 方案评审"——你根本没做过。这不是 bug，是 LLM 的本性（第一篇 1.3 讲过：它被训练成"怕交白卷"）。

**修法（现在就改你的 SKILL.md）**：把护栏从"禁止编造"一句空话，升级成**可执行的核对步骤**：

```markdown
3. 输出前自检（逐条执行）：
   a. 把每条"完成事项"与 git log 输出逐条比对，删掉没有任何提交支撑的条目；
   b. "下周计划"每条标注（推断），提示读者这些不是承诺。
```

改完重测。**预期看到**：编造条目消失。

**这就是"纪律"的本质**：不是喊口号（"不要编造！"），而是**给模型一条可机械执行的自查路径**。

> **大师对照**：qa-skills 把这个思想放大成整套**证据体系**——每条结论标注证据等级（E0 用户口头说的 < E1 文档 < E2 代码 `文件:行` < E3 运行结果 < E4 交叉验证），并规定"禁止不加标注直接输出'这里存在 Bug'"。你的"逐条与 git log 比对"就是它的微缩版：**证据 = 可核对的来源，幻觉的解药不是祈祷而是核对**。

### 2.2 坑二：格式漂移

这次三段、下次五段；标题一会儿 `## 完成事项` 一会儿 `**完成**`。原因：你在用文字"描述"格式，模型每次理解略有不同。

**修法**：把描述换成**字面模板**（例子胜过规则）：

```markdown
2. 严格按以下模板输出（占位符替换后删除方括号）：

   # 周报（M月D日–M月D日）
   ## 完成事项
   - [动词开头一句话]（[来源提交日期]）
   ## 下周计划
   - [一句话]（推断）
```

改完重测两次（**每次都新开会话**，否则模型记得上次的输出，测不出真实稳定性）。**预期看到**：两次输出结构一致。

### 2.3 坑三：数据不全

周报只基于 git，但你这周还开了评审会、帮同事看了方案——git 里没有。**这不是 bug，是"数据源边界"问题**，暂时记下来（第五章会回来），现在先在模板末尾加一行：

```markdown
   > 数据来源仅限 git 提交。会议/评审等未入库的工作请在对话中补充。
```

诚实声明边界，好过假装完整。

**Recap**：质量问题的修法分三级——编造用"可执行核对"治，格式用"字面模板"治，数据边界先"诚实声明"。

## 第三章 技能长大了：膨胀，以及第一次重构

> **本章 Success check**：你的 SKILL.md 超过 100 行后，你会把它拆成"流程 + 参考文件"两层，并理解为什么要这么拆。

### 3.1 刻意把它养胖（跟着做）

现在让需求升级，往 SKILL.md 里继续加内容——**别怕加乱，这一步就是要让它膨胀**（学 debs build-along 教程的做法：先制造痛点，再引入解药）：

- 不同团队周报格式不同 → 加"格式 A（互联网团队）/ 格式 B（传统团队）"两套模板；
- 加"数据来源"一节：git 提交、待办清单路径、日历文件的读取方法，各 10 几行；
- 加"措辞规范"：用"推进"不用"做了"、量化优先、避免流水账，又 20 行；
- 加 FAQ："跨周项目怎么算？""周报里能放风险吗？"……

加到 **100 行以上**再停。

### 3.2 观察症状（先别修，先感受）

连跑几次周报，留心三件事：

1. **变慢了**：每次触发，整份 100+ 行全文进上下文——哪怕这次根本用不到"格式 B"；
2. **变笨了**：措辞规范第 7 条和 FAQ 第 3 条打架（一个说"量化优先"，一个说"周报别堆数字"），模型随机执行其中一个；
3. **格式偶尔又漂了**：规则太多，重要的那条被稀释。

这三条症状有共同的名字：**指令过载**。qa-skills 的设计文档引用了 Red Hat 的实测：**SKILL.md 超过 500 行后 Agent 性能退化**——"试图覆盖整个领域的全能型 Skill 往往使性能退化"。你只用了 100 行就摸到了缩影。

### 3.3 重构：拆出第一层（每拆一块，先问"它为什么在这里待不住"）

规则：**每次触发都要走的，留在 SKILL.md；只在一部分情况下要走的，搬出去、留一句指路。**

新建 `~/.agents/skills/weekly-report/` 下的结构：

```text
weekly-report/
├── SKILL.md              # 只留：触发说明 + 5 步流程 + 模板（约 40 行）
├── references/
│   ├── formats.md        # 格式 A / 格式 B 两套模板（开工时问用户用哪套，再去读）
│   └── wording.md        # 措辞规范 + FAQ
└── scripts/
    └── collect.sh        # 数据收集脚本
```

逐块搬迁，**每块搬迁前先回答"为什么"**：

| 内容 | 去哪 | 为什么 |
| --- | --- | --- |
| 5 步流程 | 留在 SKILL.md | 每次触发都要走，是主干 |
| 格式 A/B | `references/formats.md` | 每次只用一套，另一套是死重 |
| 措辞 + FAQ | `references/wording.md` | 写草稿那一步才需要，收尾核对时不需要 |
| git 读取命令 | `scripts/collect.sh` | 你每次都在重复"读提交+按天分组"，**这正是上一篇说的"重复劳动固化成脚本"**；且脚本不进上下文，只有输出进 |

SKILL.md 里留指路（这叫**显式引用**，不是"可选参考"）：

```markdown
2. 数据收集：运行 bash scripts/collect.sh
3. 起草：按用户选择的格式整理（格式定义见 references/formats.md，此时读取）；
   措辞按 references/wording.md 执行全部规则（此时读取）。
```

`collect.sh` 内容：

```bash
#!/usr/bin/env bash
# 收集最近 7 天提交并按天分组，供周报技能使用
set -euo pipefail
git log --since="7 days ago" --no-merges \
  --pretty=format:"%ad|%s" --date=format:"%m-%d %H:%M" \
  | awk -F'|' '{ split($1, t, " "); day=t[1];
      if (day != prev) { print "\n## " day; prev = day }
      print "- " $2 }'
```

（记得 `chmod +x scripts/collect.sh`。）

重测。**预期看到**：产出质量不低于拆分前，甚至更好（干扰指令少了）；如果某个格式忘了应用，说明你的"此时读取"指路不够醒目——把它加粗、独立成行，再测。

### 3.4 刚才学会的东西，有个名字

你刚完成的就是 skill 领域的**三层架构**（qa-skills 原文）：

```text
L1  SKILL.md 头部     触发边界：什么时候用、什么时候不用
L2  SKILL.md 正文     工作流：每次触发都要走的主干（qa-skills 红线：≤500 行，CI 强制）
L3  references/ 等    方法/规则/模板：按需加载，工作流步骤里显式引用
```

**Recap**：膨胀是必然的（需求会长大），解药不是删内容而是**分层**；判断标准一句话——"每次都要走的留正文，部分情况才要的搬出去"；搬出去≠降级，必须在工作流里显式引用。

> **大师对照**：qa-skills 的 `test-case-writing/SKILL.md` 通篇都是这种结构——"设计方法选择（此时加载 `../core/testing-principles.md`）""可读性自检：执行 `../core/executability.md` 全部检查项，**不是可选参考**"。它还有一条 CI 校验（`validate_skills.py`）：SKILL.md 超 500 行、缺少"When NOT to Use"、引用了不存在的文件——**直接报错拒绝合并**。你现在的手工纪律，它用脚本固化成了流水线。

## 第四章 从 1 个到 5 个：触发竞争与共享库

> **本章 Success check**：你拥有日报/周报/月报/站会 4 个执行技能 + 1 个编排技能，且说"帮我整理本周汇报"和"写个站会稿"会命中不同的技能。

### 4.1 长出一个家族（复制改造，10 分钟）

以 weekly-report 为模板复制出：

```bash
cd ~/.agents/skills
cp -r weekly-report daily-report
cp -r weekly-report standup
```

改三处，各自成技能：

| 技能 | name / 触发词改为 | 流程差异 |
| --- | --- | --- |
| `daily-report` | "日报、昨天干了啥、今日总结" | `--since="1 days ago"`；三段改为"今日完成 / 明日计划 / 阻塞" |
| `standup` | "站会、standup、同步一下进度" | 三段固定"昨天 / 今天 / 阻塞"，每段 ≤3 条，30 秒能说完 |

（月报 monthly-report 同理，汇总周报文件——先建目录占位，第六章前完成即可。）

### 4.2 现在踩触发竞争的坑（必然会踩）

测这句话：**"帮我整理下这周的工作汇报"**。

症状：`daily-report` 和 `weekly-report` 的 description 里都有"整理""干了啥""汇报"——**两个技能都想接**，Agent 随机选一个，或者都读进来（正文双份进上下文）。

这正是 qa-skills 设计文档里的原话：**"没有负向约束的触发竞争会让整个体系形同虚设。"**

### 4.3 修法一：反触发（每个 description 加"不用"段）

给每个技能的 description 补上"不用于"（对照表先写清楚再改）：

```markdown
---
name: daily-report
description: 生成当天/单日工作日报。凡用户提到"日报、昨天干了啥、今日总结"时使用。
  不用于：跨多天的汇总（→ weekly-report）、站会同步（→ standup）、
  端到端整理汇报材料（→ report）。
---
```

weekly-report、standup 同样各加一段。**重测刚才那句话**——预期只命中一个。

### 4.4 修法二：加一个"编排"技能（解决"一句话终态需求"）

还有一种用户说法没人接得住："**帮我准备本周向上汇报的材料**"——它不是日报也不是周报，是"收集 → 周报 → 挑亮点 → 排版"的**组合流程**。这类"终态意图"需要一个新的薄技能来路由。

新建 `~/.agents/skills/report/SKILL.md`：

```markdown
---
name: report
description: 端到端汇报材料入口：用户说"帮我准备汇报材料/整理本周汇报/生成给老板的周报"
  时使用，编排数据收集→周报→亮点提炼→定稿的完整流程。只要单一产出
  （日报/站会/月报）→ 直接用对应技能，不用本技能。
---

# 汇报编排

本技能是薄编排：不含任何汇报写作知识（全在执行技能里），只做路由和调度。

## 流程

1. 意图识别：终态汇报 → 继续本技能；单产物 → 移交对应技能后退出
2. 调用 weekly-report 生成周报草稿（读取其产物文件）
3. 提问用户："本周要突出哪 1–2 个亮点？"（⏸ 等待答复，不代答）
4. 按答复改写草稿，输出最终材料

## 硬规则

- 不替用户决定"突出什么"——这是用户的责任，你只提案
- 你的失败只可能是编排错误，不可能是写作错误
```

注意它的两个特征（都是 qa-skills 的原设计）：**description 独占终态意图词**；**正文自我声明"我是薄编排，不含领域知识"**——这条自我声明会在出问题时救你：排查 bug 时先问"是路由错了还是写作错了"，两类问题分开修。

### 4.5 修法三：抽共享库 core/（这一步你是"被迫"的）

现在去改 daily-report 的措辞规范，你会发现 `references/wording.md` 有**三份拷贝**（daily/weekly/standup 各一），改一处忘两处。

**共享内容的下沉规则**（qa-skills 原文，两条）：

1. **被两个以上技能消费的内容才下沉**（防止过早抽象）；
2. **技能之间禁止互相引用**——共享内容一律走 core/（保证每个技能自包含）。

动手：

```bash
mkdir -p ~/.agents/skills/core
mv ~/.agents/skills/weekly-report/references/wording.md ~/.agents/skills/core/
# 删除另外两份拷贝；scripts/collect.sh 同理下沉（参数化天数）
```

各技能的引用路径改为 `../core/wording.md`。再给 core 一个"我是依赖单元"的声明（防止它被当成技能触发）：

```markdown
---
name: core
description: 汇报套件共享知识库（措辞规范、数据收集脚本）。仅在套件内被
  按需引用，任何汇报任务都不要独立触发本技能，独立使用无意义。
---
```

**Recap**：多技能的三大件——反触发（description 划清"不用时交给谁"）、薄编排（独占终态意图词，不含领域知识）、core 下沉（两处以上消费才下沉，禁止技能互引）。

> **大师对照**：qa-skills 就长这样——`qa` 是薄编排（"它失败的唯一合理原因是编排错误，不是测试判断错误"），10 个执行技能各管一段，`core/` 收拢证据规范/风险模型/可执行性标准等共享资产（CI 校验"新文件需至少两个 skill 消费才准进 core"）。你刚用 30 行走完了它 10 个技能的结构逻辑。

## 第五章 给它纪律：把"质量"变成可检查的规则

> **本章 Success check**：你的套件有一条"一票否决"标准和一个"检查点"，你可以说清楚它们和口号的区别。

到目前为止我们修的都是**执行层**问题（触发、格式、编造）。还差一层：**什么算"好的产出"？** 没有这个定义，模型永远在"看起来不错"和"其实不行"之间摇摆。

### 5.1 定你的"一票否决"（先看一个反面案例）

qa-skills 调研发现 AI 写测试用例最大的毛病是"**看似专业、实则无法执行**"——入口是虚构的、数据是占位符、判定无时限。它的对策不是喊"要专业"，而是定义一句话标准加 8 条硬规则：

> **"没读过需求、没人讲解的人，拿着文件能直接开工。"** ——不可执行的用例，覆盖再全也计零分。

现在给你的汇报套件定同款标准。想一想：汇报材料的"看似专业实则致命"是什么？——**编造**（第二章修过）和**不可追溯**（领导问"这个数据哪来的"答不上）。

写入 `core/quality.md`（新建）：

```markdown
# 汇报质量标准（一票否决项）

核心标准：产出中每一条工作陈述，都能回答"证据是什么"。

1. 每条"完成事项"必须能指到来源（提交记录 / 用户提供 / 待办清单），无来源即删除
2. 每个数字必须与来源一致，禁止四舍五入到更好看
3. "下周计划"必须显式标注（推断/待确认），不得混入完成事项
4. 输出前逐条自检 1–3，任何一条不过 → 修正后再输出
```

### 5.2 定你的"检查点"（哪些事必须人来裁决）

哪些决定**不能让模型代答**？qa-skills 列了四类（Bug 定性、执行策略、预算、澄清），你的汇报套件至少有一类：

> **"哪些工作值得写进向上汇报？"**——这是政治判断，不是文本判断。模型不知道你老板关心什么。

在 `report/SKILL.md` 流程第 3 步你已经有了雏形（⏸ 等待答复），现在把检查点正式化——特征是**"提案 + 等待 + 落盘后不得推翻"**：

```markdown
3. ⏸ 亮点裁决检查点：列出本周所有候选工作（附数据），提案 1–2 项，等用户选择。
   用户的选择落盘到材料中，后续步骤不得改写用户已裁决的内容。
```

**Recap**：纪律 = 一票否决（把质量变成机械可查的规则）+ 检查点（把"人的责任"显式圈出来，模型只提案不代答）。

> **大师对照**：qa-skills 的四类检查点全部是"⏸ 呈现提案 → 等用户 → 裁决落盘 → 后续不得推翻"。它的证据体系还有一个精妙区分值得学走：**用户随口说的（低证据，可被 git 数据推翻）≠ 用户在检查点上的裁决（是决策，不可推翻）**——前者是输入，后者是命令。

## 第六章 证明它有用：最小评测

> **本章 Success check**：你有 2–3 个带标准答案的测试任务，跑过一轮 On/Off 对照，知道自己的技能"好多少"，也见识过"单次对比是噪声"。

### 6.1 为什么必须评测（一个真实教训）

qa-skills 实测过一个教训：单次对比显示 skill 带来 **+28.8pp** 提升，激动地复验（多样本）后发现是**抽样噪声**，真实增益 +6.2pp。**没有评测的迭代是凭感觉，单次评测是赌博。**

### 6.2 最小评测（30 分钟能做完的版本）

**第一步：攒黄金集**（2–3 个带"标准答案"的真实任务）。比如：

```text
任务 1：对 <某个真实仓库> 生成本周周报
  标准答案要点：本周真实提交清单（git log 可查）+ 你心里的合理分组
任务 2：用同一仓库生成周一站会稿（30 秒能说完的量）
  标准答案要点：≤9 条、昨天/今天/阻塞三段、无编造
```

**第二步：On/Off 对照**。同一模型、同一任务，跑两遍——关掉技能（把 `~/.agents/skills` 暂时移走）一遍，开着一遍。

**第三步：逐条对照标准答案打分**，记下三类数字：命中了几条要点 / 编造了几条 / 格式是否合规。

**第四步（重要）：每个任务跑 2–3 次**，看结果的**波动**——波动大说明你的 SKILL.md 纪律还不够硬（通常是模板或自检步骤不够"机械"）。

### 6.3 评测的另一面：看清代价

你的 On/Off 对比里，一定观察得到"有技能更慢、多花 token"——qa-skills 如实披露自己是 **3.3× token 成本**。评测不只回答"有没有用"，也回答"**值不值**"：周报这种高频任务，3 倍 token 换"零编造 + 稳定格式"，通常值。

**Recap**：黄金集（带标准答案）→ On/Off 对照 → 逐条打分 → 多次跑看波动；反向结果和成本如实记录。

> **大师对照**：qa-skills 把这一步放大成了完整 benchmark 体系——12 任务黄金集、n=3 采样、预注册冻结门（阈值在验证前定死，不因数据改门）、跨模型增益下限当北极星（"对单一模型迭代出的提升若不能跨模型复现，视为过拟合而非进步"）。你的 4 步最小版就是它的骨架。

## 第七章 回望：你造的东西 vs qa-skills

到这里，把你一路做的决定和 qa-skills 的设计决策对上——**现在再看这张表，每一行你应该都有"手感"了**：

| 你做的（汇报套件） | qa-skills 做的（测试框架） | 共同的设计原则 |
| --- | --- | --- |
| 20 行最小周报跑通 | 先跑通再演进 | 第一步小到 10 分钟 |
| "逐条与 git log 比对"护栏 | 证据体系 E0–E4 + 裁决规则 | 反幻觉靠可执行的核对，不靠口号 |
| 字面模板锁格式 | 用例格式规范（case-format.md） | 例子胜过规则 |
| 100 行膨胀 → 拆三层 | 500 行红线（CI 强制） | 指令过载是性能敌人 |
| 复制出日报/站会/月报 | 9 个阶段技能各管一段 | 宁窄而深，不做全能 |
| description 加"不用于" | 每个 skill 必有 When NOT to Use | 触发竞争让体系失灵 |
| report 薄编排技能 | qa 编排入口 | 终态意图词独占；编排不含领域知识 |
| wording.md 三份拷贝 → core/ | core/ 共享知识库（≥2 消费才收） | 单一维护源；禁止技能互引 |
| core/quality.md 一票否决 | executability.md 8 条硬标准 | 先定义什么叫合格 |
| ⏸ 亮点裁决检查点 | 四类检查点（Bug 定性/执行策略/预算/澄清） | 人的责任模型不代答 |
| 4 步最小评测 | 黄金集 + 预注册门 + 跨模型下限 | 没有度量的迭代是凭感觉 |

还有两件事它做了、你暂时没做（作为你继续进阶的地图）：

1. **文件即流水线状态**：它每个阶段的产出落盘为文件，下一阶段只消费文件不靠会话记忆——所以中断后新会话读文件就能续跑。你的 report 编排目前还是"会话内接力"，月报要汇总 4 份周报文件时，你会自然走向这条设计（把日报写成文件、周报读日报文件）；
2. **类型决策矩阵（全轴必答）**：它发现模型制定测试策略时"提到"性能和安全却从不"决策"，于是设计十轴矩阵强制逐轴表态（纳入挂信号/排除留痕），最弱模型类型查全率 0 → 0.88。你的版本可以是"汇报十问"（本周数据/风险/阻塞/求助/老板关心点……每问必答）——当你发现周报总漏掉某一栏时，自然会发明它。

## 卡住了怎么办（Troubleshooting 汇总）

| 症状 | 原因 | 修法 | 章节 |
| --- | --- | --- | --- |
| 口语说法不触发 | description 缺触发词 | 补"用户会自然说的话" | 1.2 |
| 编造工作条目 | 护栏是口号不是动作 | 逐条与来源比对的机械自检 | 2.1 |
| 格式时好时坏 | 用描述而不是模板 | 字面模板 + 新会话复测 | 2.2 |
| 规则打架/变笨 | 指令过载 | 拆三层，显式引用 | 3.3 |
| 两技能抢同一句话 | 无反触发 | description 加"不用于→交给谁" | 4.3 |
| "帮我准备汇报"没人接 | 缺编排入口 | 薄编排技能独占终态词 | 4.4 |
| 改规范忘同步 | 多份拷贝 | 下沉 core/，单一维护源 | 4.5 |
| 质量摇摆 | 没有一票否决定义 | 写 quality.md，逐条可查 | 5.1 |
| 对比结果时灵时不灵 | 单次采样噪声 | 每任务跑 2–3 次看波动 | 6.2 |
