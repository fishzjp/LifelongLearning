# 实战解析：qa-skills——一套生产级测试工程 Skill 框架是怎么设计出来的

> **一句话定位**：前两篇讲原理（Agent 是什么、Skill 怎么工作），本篇讲**原理怎么落地**——拆解一个真实开源项目 [qa-skills](https://github.com/fishzjp/qa-skills)（MIT 协议，10 个 skill + 共享知识库 + 评测体系），看它做了什么、为什么这么设计、好处是什么。
>
> 读完你就能回答：**给我一个专业领域，我怎么从 0 到 1 设计出这样一套 skill？**

- **零基础**：先读第一章的三个翻车现场（不需要懂测试），再看第五章的"从 0 到 1 路线图"——中间章节可以按需查阅；

## 第一章 开篇故事：为什么"帮我测试这个需求"这么难

### 1.1 三个真实的翻车现场

小助入职第一天，测试经理丢来一句话：

> "帮我测试这个需求：优惠券到期自动结束功能，仓库在那边。"

**翻车一：写出了"看似专业、不可执行"的用例。**

小助交出的用例文件漂亮极了——覆盖矩阵齐全、术语专业。但执行者拿到手第一步就卡住：

```text
TC-07-03 验证券到期逻辑
操作步骤：使用测试账号进入券管理页面，选择一张测试券
预期结果：功能正常
```

哪个页面？什么账号？哪张券？"功能正常"怎么判定？等多久？——**没读过需求、没人讲解的人，拿着这份文件根本没法开工。** 这是 AI 写测试用例最典型的质量问题：它想象了一个系统，而不是看着真实系统写。

**翻车二：把所有方法论塞进一个说明书。**

经理说："我们公司的测试方法论、用例格式、风险模型、证据规范、报告模板……全套资料都给你。"小助把这些**全部塞进一份 2000 行的指令文件**。结果：规则越多，他实际遵循的反而越少——注意力被稀释，真正重要的约束（比如"异步用例必须有判定时限"）淹没在细节里，时灵时不灵。

**翻车三：什么都会，就是不做决定。**

经理问："这个功能，性能测试和安全测试到底做不做？做多深？"

小助的策略文档里写道："性能和安全非常重要，建议关注。"——**提到了，但从未决策**。哪些类型纳入？测多深？哪些明确不测、为什么？一个字没有。后来评测证实这不是小助一个人的毛病：未装 skill 的模型在 30 次采样中**零显式类型决策**。"提到"不等于"决策"，不可审计的策略等于没有策略。

### 1.2 qa-skills 就是这三个问题的答案

[qa-skills](https://github.com/fishzjp/qa-skills) 是一个面向 Claude Code 等 Agent 的测试工程 Skill 框架，装好之后对 Agent 说一句"帮我测试这个需求"，就能跑通从需求理解到测试报告的完整流水线。它的自我定位不是"几个测试 Prompt"，而是：

> **方法论（沉淀在 core/）+ Skills（只做工作流编排）+ Benchmark（用数据回答到底有没有用）三层体系。**

三个翻车现场对应三组解法，本章先给一句话版，后面逐个拆：

| 翻车 | 解法 | 对应设计 |
| --- | --- | --- |
| 用例不可执行 | **可执行性一票否决** + 8 条硬标准 + 代码优先 | `core/executability.md` |
| 规则越多遵循越少 | **10 个窄 skill + 500 行红线 + 按需加载** | 三层架构 L1/L2/L3 |
| 不做决策 | **类型决策矩阵：十轴全轴必答** | `core/test-type-matrix.md` |

## 第二章 全景：qa-skills 做了什么

### 2.1 目录结构（先看长相）

```text
skills/                     # 产品本体：10 个 skill + 1 个共享知识库
  qa/                       # 编排入口（薄，不含任何测试知识）
  core/                     # 共享知识库（不触发，只被引用）
    evidence.md             #   证据分级 E0–E4 与裁决规则
    risk-model.md           #   风险评级模型（评级必须挂证据）
    executability.md        #   可执行性 8 条硬标准（一票否决）
    test-type-matrix.md     #   类型决策矩阵（十轴全轴必答）
    case-format.md          #   用例编号与格式规范
    ……                      #   coverage / clarify-pattern / report-template 等
    methods/                #   设计方法细则（边界/数据驱动/权限/状态机）
    scripts/                #   validate_schema.py + scan_signals.py
  requirement-analysis/     # 阶段 skill：需求建模
  test-strategy/            # 阶段 skill：风险分析 + 两域决策
  test-case-writing/        # 阶段 skill：写用例（双轨产物）
  test-case-review/         # 阶段 skill：独立审查存量用例
  automated-e2e-testing/    # 阶段 skill：转 Playwright 自动化
  api-testing/              # 阶段 skill：接口级测试
  exploratory-testing/      # 阶段 skill：charter 驱动探索
  bug-analysis/             # 阶段 skill：Bug 根因定位
  regression-testing/       # 阶段 skill：diff → 回归范围
```

### 2.2 流水线（它跑起来什么样）

用户说"帮我测试这个需求"，`qa` 这个编排入口把任务翻译成 9 个阶段，每个阶段产出落盘为文件：

```text
PRD / 代码
   │  requirement-analysis     ↓ 产出：需求模型.md          ⏸ 澄清检查点
   │  test-strategy            ↓ 产出：测试策略.md           ⏸ 预算裁决
   │  test-case-writing        ↓ 产出：测试用例 markmap + schema.yaml
   │  test-case-review         ↓ 产出：修订后用例 + 审查记录
   │  ⏸ 执行策略裁决（手动 / Playwright / API）
   │  automated-e2e / api      ↓ 产出：可运行代码 + 执行结果
   │  bug-analysis             ↓ 产出：Bug 条目（根因/证据/回归） ⏸ Bug 定性
   │  regression-testing       ↓ 产出：回归清单.md
   └→ 测试报告.md
```

每个阶段也**独立可用**——"帮我审一下这份用例"只命中审查 skill，不强制走全流水线。

### 2.3 实测效果（包括反向结果，如实披露）

同一模型、同一评测链路，唯一差异是是否注入本框架（12 任务黄金集）：

| 指标 | 无 Skill | 有 Skill |
| --- | --- | --- |
| 用例规格符合度 | 0.26 | **0.98** |
| E2E 代码真实执行（3 采样） | 0/3 可运行 | 1 全过 + 2×(2/3) |
| 植入 Bug 检出率 | — | **75%** |
| 类型查全率（最弱模型，决策层首轮） | **0**（宽容口径也是 0） | **0.88** |
| API 代码真实执行通过率 † | **74%** | 52%（反向！后定案为评测任务缺陷，修复后 100% vs 99.2%，差距消除） |
| Token 成本 | 1× | 3.3×（更好但更贵） |

注意这个表格的诚实度：**反向结果和成本代价都写在 README 正文中**，不是藏在附录里。这个"评测要诚实"的姿态本身就是设计的一部分（3.9 节）。

## 第三章 核心章节：九大设计决策逐个拆解

每个决策都按同一个格式讲：**遇到什么问题 → 备选方案 → 实际选择 → 为什么 → 好处**。这九个决策是可以迁移的——换成法律、医疗、运维任何领域，思考方式通用。

### 决策一：10 个窄 skill + 薄编排，不做 1 个全能 skill

- **问题**：测试是个大领域（需求分析、策略、用例、审查、自动化、Bug 定位、回归……），塞进一个 SKILL.md 会怎么样？
- **备选**：① 一个全能 skill，把所有方法论写进去；② 按阶段拆成多个窄 skill，加一个编排入口。
- **选择**：②。而且立了一条硬红线：**SKILL.md ≤ 500 行**（由 `validate_skills.py` + CI 强制，不是风格建议）。
- **为什么**：外部实践（Red Hat ACE 团队 2026-07 的总结）验证了——**L2 指令超过 500 行后 Agent 性能开始退化**，"试图覆盖整个领域的全能型 Skill 往往使性能退化"。超出遵循能力的规则只是噪音，还会稀释真正重要的约束。这正好对应我们第一篇讲的 context rot：白板上塞得越多，看得越糊。
- **好处**：每个 skill 职责单一、可独立测试、可独立触发；编排层（`qa`）失败的原因只剩"编排错误"，排查时不用怀疑测试知识写错了。

一句话记法：**宁窄而深，不做全能。**

### 决策二：core/ 共享知识库——"被两个以上 skill 消费的内容下沉"

- **问题**：证据规范、用例格式、风险模型……好几个阶段 skill 都要用。各写一份？还是互相引用？
- **选择**：建一个 `core/` 目录收拢所有共享内容，立规矩：**新文件需至少两个 skill 消费才准进 core/**；并且**禁止跨 skill 引用兄弟 skill 的文件**（CI 强制）——被共享就下沉，不许 skill 之间互相拉扯。
- **为什么**：单一维护源。证据体系如果散在 5 个 skill 里各写一份，改一次要同步五处，必然漂移。而 core/ 有自己的 SKILL.md，但**只作为"安装依赖单元"存在**——它的 description 明确写着"不要独立触发我，独立使用无意义"（还记得第二篇的 `disable-model-invocation` 思想吗？这里是靠 description 措辞实现同样的效果）。
- **好处**：方法论专家只维护一份 `evidence.md`，10 个 skill 全部受益；安装器知道装任一 skill 必须连 core/ 一起装（否则相对路径断裂）。

### 决策三：文件即流水线状态——长流水线不依赖上下文

- **问题**：9 个阶段跑下来，对话上下文早就爆炸了；中途断线、换会话怎么办？
- **备选**：① 靠会话记忆传递中间结果；② 每阶段产出落盘为文件，下阶段只消费文件。
- **选择**：②，并配一条编排纪律：**每个阶段运行在独立上下文（子代理）中，任一时刻活跃指令 ≤ 1–2 个 skill**；宿主不支持子会话时**自动降级**为顺序会话 + 文件衔接——正确性不受影响，损失的只是上下文卫生。
- **为什么**：这正是第一篇 6.3 节"结构化笔记"和子代理思想的直接落地。上下文窗口是稀缺且不可靠的（会断、会压缩、会腐烂），**磁盘文件才是可靠的状态存储**。
- **好处**：三重身份——断点续跑（新会话读文件即可继续）、阶段间上下文隔离的传递介质、回归追溯的数据基础（Schema 里的 code_refs 记录"用例 ↔ 代码"映射，回归时直接反查影响面，而不是"让模型读一遍 diff 猜"）。

一句话记法：**状态在文件里，不在聊天里。**

### 决策四：证据体系 E0–E4——给"幻觉"套上笼头

- **问题**：AI 做测试分析时爱下断言："这里存在 Bug！"——依据呢？没有。怎么压制这种幻觉式结论？
- **选择**：全框架统一一套证据语言（`core/evidence.md`）：

```text
E0  用户初始陈述   ← 未经核实的用户描述（最低）
E1  文档证据      ← PRD / 设计文档 / FAQ
E2  代码证据      ← 文件:行、接口签名
E3  运行证据      ← 实际执行结果、日志、截图
E4  交叉验证      ← 多来源互证（最高）
```

加上三条裁决规则：**静态问题（代码怎么写的）E2 为王；动态问题（系统怎么表现）E3 为王；意图问题（应该是什么行为）用户的澄清裁决说了算**。并规定：**禁止不加标注直接输出"这里存在 Bug"**。

- **一个精妙的细节**：E0（用户随口说的）是低证据、可以被代码推翻；但用户在澄清检查点上的**裁决不是证据，是决策，不可推翻**。这个区分避免了"后续阶段又拿代码把用户已裁决的事翻出来重吵一遍"。
- **好处**：每条结论可追溯（证据 → 风险 → 策略 → 用例的推导链全程有据可查）；幻觉被制度性地暴露——模型要么挂上证据，要么明说这是 hypothesis（待验证假设）。

### 决策五：可执行性一票否决——先定义"什么叫合格"

- **问题**：第一章翻车一。AI 生成的用例"看似专业、实则无法执行"。
- **选择**：把产出标准压成一句话——**"没读过需求、没人讲解的人，拿着文件能直接开工"**——然后落成 8 条硬标准（`core/executability.md`）：代码优先（先读真实实现再写用例，不凭 PRD 想象系统）、具体数据禁占位符、页面可达性、异步判定必须有时限（"到期后 1 小时内状态变为已结束，超 1 小时判失败"）、断言范围不得超过验证强度（两个样本不许断言"全局唯一"）、前置可得性（环境/账号/数据从哪来，拿不到就写 TODO 指明找谁）……
- **评测里它是扣分狠手**：不可执行的用例，覆盖再全也计零分。
- **为什么有效**：它把"质量"这个模糊概念变成了**可检查的机械规则**。模型不需要理解"什么叫专业"，只需要逐条对照 8 条标准自查。
- **额外好处——执行模型判定**：开工先判断"这功能有没有 UI"。无 UI 的后端功能（定时任务、数据 stage）测试工程师根本无法独立执行，用例就写成"测试-开发协作清单"（步骤标"请开发执行"、预期标"请开发反馈查库结果"）。这一条拦住了大量"照搬 UI 用例写法"的空中楼阁。

### 决策六：双轨产物——markmap 给人，schema.yaml 给机器

- **问题**：测试用例有两个消费者：测试工程师要人读的文件，下游 skill（审查/回归/执行）要机器可读的结构。维护两份？
- **选择**：**markmap 文件是唯一人工维护源；schema.yaml 由 skill 从 markmap 单向抽取，永远可以再生**。人只维护一份，机器的那份是衍生物。
- **为什么**：双份人工维护必然漂移（改了这份忘那份）。单向抽取 + `validate_schema.py` 校验（YAML 合法性 + 编号一致性 + 占位符检查），保证了机器层永远可信。
- **好处**：三类消费者各取所需——测试工程师读 markmap 开工；`test-case-review` 用 Schema 算覆盖分母；`regression-testing` 用 `code_refs`/`risk_ref` 做影响面分析。这又是第二篇 8 章思想的放大版：**脚本/结构化产物不占上下文，输出即接口**。

### 决策七：类型决策矩阵——"全轴必答"治不决策

- **问题**：第一章翻车三——模型"提到"性能和安全，但从不决策。
- **选择**：设计一张**十轴矩阵**（性能/业务安全/可靠/并发/兼容/无障碍/视觉/国际化/迁移/契约），立三条铁律：
  1. **全轴必答**：每个轴必须给出 include / exclude / handoff 三选一的显式决策，缺轴不过校验——**不漏测靠"没考虑到的类型必须留下没考虑的痕迹"**；
  2. **纳入必须挂信号，排除必须留理由**（引用扫描结果）——不浪费靠双向留痕；
  3. **full 档有预算上限**（防"样样都测最深的伪安全策略"）。
- **弱模型机制（最巧妙的部分）**：代码信号分两级——**G 级（可 grep 的）由脚本 `scan_signals.py` 机械扫描**，生成预填表，模型**从预填表修订而不是从空白生成**；S 级（语义模式）由模型照单复核。"脚本无命中"单独不构成排除依据，防脚本盲区被制度化为漏测。十轴矩阵本身按轴独立成节，**分轴组推进时只加载本组小节**——300 行矩阵不整文件进上下文（渐进式披露用到极致）。
- **实测**：最弱模型类型查全率 **0 → 0.88**；其中需求未提、只存在于代码里的可靠性/契约轴 **0 → 8/9**。
- **为什么有效**：它把"专家直觉"变成"流程纪律"。专家不是什么测试都会做，而是**每个类型都进过决策、每个决策都有证据、不做的留痕**。

### 决策八：人在环路的检查点——Agent 只提案，不代答

- **问题**：Bug 是缺陷还是预期行为？用例手动执行还是转自动化？预算超了砍哪个？这些是**人的责任**，Agent 代答等于埋雷。
- **选择**：四类检查点（澄清、执行策略、Bug 定性、预算裁决）一律**暂停等用户答复**；裁决落盘后，后续阶段不得推翻。
- **好处**：责任边界清晰。配合 `clarify-pattern.md` 的提问规范（逐条独立成卡、给建议选项），用户裁决的成本也被压到最低。

### 决策九：评测驱动迭代——先建"有没有用"的尺子，再堆功能

- **问题**：怎么知道这套 skill 到底有没有用？改了一版是变好还是变坏？
- **选择**：本地维护完整评测链路（黄金集 + harness + 单测），方法论极其较真：
  - **多样本（n=3）量化方差**——实测过单采样 +28.8pp 的表观增益被复验证实是噪声，实际 +6.2pp；
  - **门预注册冻结**——阈值在验证轮之前冻结，验证按冻结门判定，**不因数据改门**；
  - **失败模式归类驱动迭代**——bench 的产出是"改哪里"，不是总分；
  - **北极星指标是跨模型增益下限**——在单一模型上迭代出的提升若不能跨模型复现，视为**过拟合而非进步**；
  - **反向结果如实披露**（见 2.3 表格的 API 52% 和 3.3× 成本）。
- **为什么**：没有度量的迭代是凭感觉。skill 和代码一样会回归——"改一处、坏三处"没有评测根本看不见。

## 第四章 与前两篇原理的对照（理论落地验证）

这一套设计里，前两篇的每个核心概念都能找到实例：

| 前两篇的原理 | qa-skills 中的落地 |
| --- | --- |
| 渐进式披露（三层） | L1 触发边界 / L2 工作流 ≤500 行 / L3 core+references 按需加载 |
| description 是触发钩子 | 每个 skill 的 description 写清"什么时候用、什么时候不用、交给谁"（触发/反触发表） |
| When NOT to Use（反触发） | 硬性要求：没有负向约束的触发竞争会让体系形同虚设；CI 校验每个 SKILL.md 必须有该段 |
| context rot / 白板稀缺 | 500 行红线、阶段间上下文隔离、矩阵分轴加载、澄清仪式削减（实测省掉仪式净收益 +13.5pp） |
| 文件即状态（结构化笔记） | 每阶段落盘产物，断点续跑只认文件 |
| 子代理隔离 | Explore 代理矩阵并行做代码审查；每阶段独立上下文 |
| 脚本不进上下文 | scan_signals.py 扫 G 级信号出预填表；validate_schema.py 机械校验 |
| 错误回填给模型 | 澄清检查点：把"文档与代码不一致"列成问题卡等用户裁决 |
| 评测驱动（skill-creator 方法学） | On/Off 对照 + 黄金集 + 预注册门，放大成完整 benchmark 体系 |
| Skill ≠ Prompt（TRAE 三误区） | 工作流 + 决策纪律 + 产物 schema，而不是一段提示词 |

特别值得注意的一个**反常识发现**（来自它的单文件消融实验）：**只提供核心标准文档（纯知识）不改变模型行为——0.26→0.98 的增益来自"工作流 + 决策纪律"**。这印证了第二篇 10.4 的观点：skill 的灵魂是流程和约束，不是资料堆砌。

## 第五章 从 0 到 1：设计你自己的 skill 套件（路线图）

把 qa-skills 的做法提炼成七步。假设你要给"法律合同审查"做一套 skill（任何专业领域同理）：

### 第 1 步：定使命（一句话）

> 装上这套 skill 后，对任何 agent、任何模型，在合同审查领域带来质的提升。

所有后续决策（加什么、砍什么）都拿这句话当锚。没有使命，skill 会膨胀成大杂烩。

### 第 2 步：把终态任务拆成阶段，一阶段一个窄 skill

问自己：用户的一句话终态需求是什么？（"帮我审这份合同"）中间要经过哪些**不同专业动作**？

```text
合同审查 → ① 合同类型识别与要素提取  ② 条款风险分析
           ③ 引用法规核验  ④ 修订建议起草  ⑤ 复审与报告
```

每阶段一个 skill 目录。**红线：SKILL.md ≤ 500 行，超了就说明该拆或该下沉**。再写一个薄的编排 skill 独占终态意图词（"帮我审合同"），只做调度不含专业知识。

### 第 3 步：给每个 skill 写触发边界（比写正文更重要）

每个 SKILL.md 必须回答三个问题：**什么时候用 / 什么时候不用 / 不用时交给谁**。

```markdown
---
name: clause-risk-analysis
description: 分析合同条款的法律风险时使用——识别不利条款、缺失条款、
  与法规冲突项。不用于：合同要素提取（contract-parsing）、修订建议
  起草（revision-drafting）、端到端审查（legal-qa 编排）。
---
```

没有"交给谁"的反触发，多个 skill 的 description 必然重叠，触发竞争会让整个体系失灵。

### 第 4 步：抽共享层（core/）

写着写着你会发现：证据分级、风险评级模型、报告模板……好几个 skill 都在用同一套东西。此时建 `core/`，规矩两条：

- **至少两个 skill 消费的内容才下沉**（防止过早抽象）；
- **禁止 skill 之间互相引用**——共享内容一律走 core/（保证每个 skill 自包含）。

core/ 自己的 SKILL.md 要明确声明"我是依赖单元，不要触发我"。

### 第 5 步：定义每阶段的产物（文件即接口）

每阶段必须落盘**命名明确**的文件，并想清楚**谁消费它**：

| 阶段 | 产物 | 消费者 |
| --- | --- | --- |
| 要素提取 | `合同要素.schema.yaml` | 风险分析（读结构化要素） |
| 风险分析 | `风险清单.md`（每条挂证据等级） | 修订建议（只处理高风险项） |
| …… | …… | 报告（汇总全部） |

人有人的格式（可读的 markdown），机器有机器的格式（可校验的 yaml），**人维护的那份是唯一源，机器份单向抽取**。

### 第 6 步：定纪律（这套 skill 的灵魂）

问三个问题，把答案写成硬规则：

1. **什么是一票否决？** qa-skills 选了"不可执行"。合同审查可能是"引用法条必须真实存在、禁止编造案号"——找到你领域里"看似专业实则致命"的失败模式，定为零分项；
2. **证据怎么分级？** 仿照 E0–E4 设计你领域的等级（如：口头陈述 < 合同文本 < 法条原文 < 判例检索结果），并写清**冲突时听谁的**；
3. **哪些决策必须留给人？** 列出检查点清单（如"风险定性为重大 / 一般必须用户确认"），Agent 只提案不代答。

### 第 7 步：建评测（哪怕最简版）

最少成本的起步：

1. 准备 3–5 个**带标准答案**的真实任务（黄金集）；
2. 同一模型**跑两遍：不开 skill / 开 skill**（On/Off 对照）；
3. 关键指标**逐条对照标准答案**，而不是"看着不错"；
4. 每次改动后复跑，**记录反向结果**——它往往指向最深的洞察（qa-skills 的 API 52% 反向结果最终定案为评测任务自身的缺陷，这个追查过程本身就是收获）。

### 避坑清单（全部来自 qa-skills 的真实踩坑）

| 坑 | 现象 | 解法 |
| --- | --- | --- |
| 仪式性输出 | 干净材料上强行走澄清流程，实测净收益 **−13.5pp** | 无问题就一句话确认，不产仪式性清单 |
| 模块坍缩 | 多模块任务写完第一个模块就交差 | 交付前逐模块核对：每个输入模块都有非空产出 |
| 维度坍缩 | 模块全了但维度空（主流程用例 2/2 丢失） | 核对下探到维度：主流程/时间双侧/负向逐条检查 |
| 数据模板自伤 | 生成的唯一名 22 字符撞上契约 maxLength 20，整条用例失败 | 测试数据按字段约束上限预留余量，不顶格 |
| 单采样噪声 | +28.8pp 的表观增益复验后证实是噪声 | n=3 起步，量化方差再下结论 |
| 全检伪执行 | 弱模型下"逐文档比对全检"是假装执行 | 降级为抽查，把关键核对内联到生成路径 |
| 过拟合单一模型 | 在一个模型上的提升换个模型就没了 | 北极星指标定跨模型增益下限 |
