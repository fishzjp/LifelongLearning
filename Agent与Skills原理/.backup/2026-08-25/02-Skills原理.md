# Skills 原理：给 Agent 的按需加载知识包

> Skill = 一个文件夹 + 一份 SKILL.md。
> 它不给模型新能力，只在恰当的时机，把恰当的知识注入上下文。

## 1. Skill 解决什么问题

上一篇讲了：上下文窗口是 agent 唯一的工作记忆，且是稀缺资源。这带来一个两难：

- **全塞进去？** 不可能。你有几十个领域的最佳实践（React 性能、PR 审查、SQL 调优、PDF 处理……），全写进系统提示，窗口直接爆炸，正常干活的空间没了。
- **都不放？** 模型用通用知识硬闯专业任务，质量不稳定——它会，但不知道你们团队的最佳做法。

注意这里缺的是**知识，不是能力**。模型本来就能读写文件、跑命令（工具已经给了能力），缺的是"这类任务在我们这儿的标准做法是什么"。

Skill 的答案：**把领域知识打包成独立文件，平时只留一行索引在上下文里，用到时才把正文加载进来。**

一个准确的类比：**工具是手，Skill 是操作手册（SOP）**。手册不会让你长出新的手，但能让你把手用对。

## 2. 物理结构：Skill 长什么样

一个 skill 就是一个目录，核心是那份 `SKILL.md`：

```text
my-skill/
├── SKILL.md          # 必需：YAML frontmatter + markdown 正文
└── (全部可选)
    ├── references/   # 详细文档，模型按需阅读
    ├── scripts/      # 现成脚本，模型直接调用，不必每次重写
    └── assets/       # 模板、样例等静态资源
```

`SKILL.md` 的解剖：

```markdown
---
name: find-skills
description: Helps users discover and install agent skills when they
  ask "find a skill for X"...
---

# Find Skills

（正文：写给模型看的工作流程和规则）
```

只有两个字段是必需的：

- **`name`**：小写中划线命名，必须和目录名一致。
- **`description`**：这个 skill 做什么、**什么情况下该用它**。这是整份文件里最重要的两行字，原因见第 4 节。

## 3. 核心机制：渐进式披露（Progressive Disclosure）

这是 Skills 设计的灵魂，一共三层：

| 层 | 装什么 | 何时进入上下文 | 开销 |
| --- | --- | --- | --- |
| 第 0 层 | `name + description` | 会话全程常驻，触发全靠它 | 每个 skill 约几十 token |
| 第 1 层 | SKILL.md 正文 | 触发后一次性注入 | 建议 < 500 行 |
| 第 2 层 | `references/` 等附属文件 | 正文指路，用到才 Read | 原则上不限大小 |

算一笔账就明白这套设计的价值：你机器上装了 40 个 skill，第 0 层的索引总开销约一两千 token——相当于读半个文件。但假如其中某个 skill 带了 3 万 token 的领域手册，只在真正触发它的那个会话里、并且只读用到的章节。

**这是典型的"索引常驻、正文按需"**，和操作系统的虚拟内存 / 惰性加载是同一个思想：稀缺资源（窗口）只放高频小件（索引），大件（正文）用到再取。

分层还带来工程上的好处：

- 写 skill 的人不用压抑篇幅——细节放进 `references/`，正文只写流程和"何时读哪个文件"；
- 模型一次只多看一小块，不会因为一个 skill 把上下文吃掉三分之一。

## 4. 触发机制：description 是唯一的钩子

skill 怎么知道"轮到我了"？完整链路：

**启动时**：harness 扫描 skills 目录，把所有 skill 的 `name + description` 收进一份清单，注入系统提示。对模型来说，这份清单就是"我有哪些手册可翻"。

**对话中**：模型读到用户请求，把请求语义和清单里的 description 做匹配。匹配上了，就调用 `Skill` 工具加载它； harness 把 SKILL.md 正文注入上下文，从下一轮起模型就"带着这份手册"干活。

**也可以显式触发**：用户输入 `/skill-name` 直接点名加载，不依赖模型自觉。

由此推出一个关键结论：**description 写得好不好，直接决定 skill 会不会被用——它就是 skill 的全部"曝光预算"**。实战经验（来自 skill-creator 的总结）：

- description 里必须同时写清 **what**（干什么）和 **when**（什么话术/场景该触发）；
- 模型倾向于**漏触发**而非误触发，所以措辞要适当"外向"一点。对比：
  - 弱："如何为内部数据构建仪表盘"
  - 强："如何构建高性能内部数据仪表盘。**凡**用户提到 dashboards、数据可视化、内部指标，或想展示任何公司数据时**都应使用**——哪怕没明说 dashboard 这个词。"
- 正文写得再好，description 没钩住触发，就等于没有。

## 5. 发现路径与优先级

ZCode 按以下顺序发现 skills（同名时高优先级生效）：

```text
<project>/.zcode/skills/     ← 项目级，最高优先级，可用来覆盖
<project>/.agents/skills/    ← 项目级，跨工具标准位置（新 skill 默认放这）
~/.zcode/skills/             ← 用户级
~/.agents/skills/            ← 用户级，跨工具标准位置
```

两条选位原则：

- 只在这个仓库有意义的 skill 放项目级；走到哪都想用的放用户级（`~/`）。
- 想覆盖某个已安装的官方 skill？把同名 skill 放进更高优先级目录即可，不必改原文件（原文件可能在只读的插件缓存里，比如 `~/.zcode/cli/plugins/cache/...`）。

## 6. 真实例子：find-skills

你机器上装的 `~/.agents/skills/find-skills/` 是个典型样本，值得拆一遍：

- **frontmatter**：description 列了一串用户可能说的话（"how do I do X"、"find a skill for X"、"is there a skill that can..."）——这是在给语义匹配喂特征，把第 4 节的触发原则落成实文。
- **正文结构**：先"When to Use"（强化触发条件），然后一步步的操作流程（查排行榜 → CLI 搜索 → 核验质量 → 呈现选项 → 代为安装），每步带具体命令。
- **可验证性**：整份正文就是一套可执行 SOP，模型照做即可，不需要发挥。

结构模板可以直接抄：**触发条件 → 分步流程 → 命令/示例 → 边界情况（没找到怎么办）**。

## 7. 写 Skill 的要点清单

来自 skill-creator 的实践总结，按重要性排序：

1. **description 先行**：写清 what + when，宁可外向不可含蓄。这是 skill 的命。
2. **正文克制**：目标 500 行以内。超了就把领域细节拆进 `references/`，正文只留流程和"何时读哪个文件"。
3. **祈使句 + 讲 why**："编辑前先读文件"比"你应该考虑……"有效；规则不明显时解释原因，现代模型理解了原因会执行得更好。满篇全大写的 MUST/NEVER 通常是规则没讲清的遮羞布。
4. **例子胜过规则**：要结构化输出？直接给一个字面示例。该用哪个工具？直接给调用样例。
5. **重复劳动固化成脚本**：如果每次执行模型都在现场重写同一个辅助脚本，就把它放进 `scripts/`，正文里指个路。写一次，次次复用。
6. **测试驱动迭代**：写完草稿，用 2–3 个真实口吻的测试提示词（带具体路径、口语化、甚至有错别字）跑一遍，看触发没触发、输出对不对，改了再跑。观察"过程"和"结果"同样重要——如果 skill 让模型原地打转、反复读同一个文件，说明规则过拟合了，该删不该加。
7. **更新时保留原 name**：`research-helper` 更新后还叫 `research-helper`，不要 `-v2`——名字是触发契约的一部分。

## 8. Skill vs 工具 vs MCP vs 子代理

四个概念各管一段，混在一起就容易选错药：

| | 本质 | 给模型什么 | 什么时候用 |
| --- | --- | --- | --- |
| **Skill** | markdown 知识包 | 知识、流程、约定 | "怎么做最好"缺指导 |
| **工具（Tool）** | harness 内置函数 | 能力（读写执行） | "能不能做"缺手段 |
| **MCP** | 标准化外部服务协议 | 第三方系统能力 | 要接入外部世界（数据库、浏览器、SaaS） |
| **子代理** | 独立上下文的分身 | 隔离 + 并行 | 探索性脏活，防上下文污染 |

一句话辨析：**缺能力上工具/MCP，缺知识上 Skill，怕污染上子代理。** 四者也常组合——一个 skill 的正文可以指挥模型调用 MCP 工具、派出子代理。

## 9. 局限与边界

诚实起见，skill 不是银弹：

- **不给能力**。模型做不到的事（比如真正渲染一张图），写多少 markdown 都没用，得靠工具。
- **触发是概率性的**。靠语义匹配就有漏网之鱼，关键流程可以靠 `/skill-name` 显式触发兜底。
- **质量上限是作者水平**。skill 只是把好做法注入上下文，没有好做法可写时它无米下锅。
- **有维护成本**。约定变了 skill 不跟着变，模型会一直照旧手册办事——过期的 SOP 比没有更糟。

## 10. 小结

| 机制 | 一句话 |
| --- | --- |
| Skill 是什么 | 文件夹 + SKILL.md，给 agent 的按需加载知识包 |
| 渐进式披露 | 索引（name+description）常驻，正文触发时加载，细节按需 Read |
| 触发原理 | 模型拿用户请求和 description 做语义匹配；description 是全部曝光预算 |
| 放哪里 | 项目级 `.agents/skills/` 或用户级 `~/.agents/skills/`，高优先级覆盖低优先级 |
| 写好它 | description 外向、正文克制、例子开路、脚本固化、测试迭代 |

回到上一篇的结尾：agent 工程的核心矛盾是"怎么花好窗口里每一个 token"。Skills 用"索引常驻、正文按需"回答了知识注入这一半；上下文压缩和子代理回答了历史膨胀那一半。三者合起来，就是一台能带着全部家当干活的机器。
