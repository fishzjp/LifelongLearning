## 什么是黑盒测试

### 定义

黑盒测试（Black Box Testing），也称为功能测试或行为测试，是一种测试方法，测试人员不需要了解程序内部的代码结构、逻辑和实现细节，只需要根据需求规格说明和功能规格说明，测试程序的功能是否符合预期。

**核心思想**：
> 把程序看作一个黑盒子，只关注输入和输出，不关心内部实现。

### 黑盒测试的特点

#### 优点

1. **不需要了解代码实现**
   - 测试人员不需要编程知识
   - 可以从用户角度测试
   - 测试与开发可以并行进行

2. **测试用例设计基于需求**
   - 直接验证需求是否满足
   - 容易发现需求理解偏差
   - 测试用例易于理解和维护

3. **用户视角**
   - 从用户使用场景出发
   - 更贴近实际使用情况
   - 容易发现用户体验问题

#### 缺点

1. **覆盖率难以量化**
   - 无法直接测量代码覆盖率
   - 可能遗漏某些代码路径

2. **测试用例可能冗余**
   - 可能设计出功能重复的测试用例
   - 需要经验判断哪些用例是必要的

3. **难以测试内部逻辑**
   - 无法测试代码的内部错误
   - 难以发现算法实现的缺陷

### 黑盒测试的适用场景

- **功能测试**：验证软件功能是否符合需求
- **集成测试**：测试模块之间的接口和交互
- **系统测试**：测试整个系统的功能
- **验收测试**：用户验收软件是否符合预期
- **回归测试**：验证修改后功能是否正常

### 黑盒测试与白盒测试的区别

| 对比项 | 黑盒测试 | 白盒测试 |
|--------|----------|----------|
| 测试对象 | 程序功能 | 程序代码 |
| 测试依据 | 需求规格说明 | 代码结构 |
| 测试人员 | 不需要编程知识 | 需要编程知识 |
| 测试覆盖 | 功能覆盖 | 代码覆盖 |
| 测试阶段 | 集成测试、系统测试 | 单元测试 |
| 发现缺陷 | 功能错误、接口错误 | 逻辑错误、算法错误 |

## 等价类划分法

### 定义

等价类划分法（Equivalence Partitioning）是一种重要的黑盒测试方法，它将所有可能的输入数据划分成若干等价类，从每个等价类中选择代表性数据进行测试。

**核心思想**：
> 如果程序对等价类中某个输入的处理是正确的，那么对等价类中其他输入的处理也应该是正确的。

### 等价类的类型

#### 1. 有效等价类

**定义**：符合需求规格说明的输入数据集合。

**特点**：
- 程序应该正确处理这些数据
- 测试程序是否实现了预期功能

**示例**：
- 用户年龄：18-65岁之间的整数
- 密码长度：6-20个字符
- 邮箱格式：符合邮箱格式规范的字符串

#### 2. 无效等价类

**定义**：不符合需求规格说明的输入数据集合。

**特点**：
- 程序应该拒绝或提示错误
- 测试程序的错误处理能力

**示例**：
- 用户年龄：小于18或大于65的整数
- 密码长度：小于6或大于20个字符
- 邮箱格式：不符合邮箱格式的字符串

### 等价类划分的步骤

1. **分析需求**：理解输入条件的要求和限制
2. **划分等价类**：将输入域划分为有效等价类和无效等价类
3. **设计测试用例**：为每个等价类设计至少一个测试用例
4. **选择测试数据**：从等价类中选择代表性数据

### 等价类划分的原则

1. **完整性**：所有可能的输入都应该被划分到某个等价类中
2. **互斥性**：不同等价类之间不应该有重叠
3. **代表性**：每个等价类中的测试数据应该能代表整个等价类

1. **边界值处理**：等价类划分后，边界值需要单独测试
2. **组合情况**：多个输入条件时，需要考虑等价类的组合
3. **异常情况**：不要遗漏异常输入，如空值、null、特殊字符等
4. **实际数据**：选择测试数据时，尽量使用真实场景的数据

## 边界值分析法

### 定义

边界值分析法（Boundary Value Analysis）是一种黑盒测试方法，它基于"缺陷往往出现在边界处"的经验，重点测试输入域的边界值和边界附近的值。

**核心思想**：
> 程序在处理边界值时最容易出错，因此应该重点测试边界值。

### 为什么边界值容易出错？

1. **编程习惯**：程序员容易在边界判断时出错（如使用`>`而不是`>=`）
2. **数组索引**：数组越界是常见错误
3. **循环条件**：循环的起始和结束条件容易出错
4. **数值计算**：浮点数精度问题在边界处更明显

### 边界值的选择原则

对于范围`[a, b]`（a为最小值，b为最大值），应该测试：

1. **正好等于边界值**：a, b
2. **刚好小于边界值**：a-1, b-1
3. **刚好大于边界值**：a+1, b+1

**示例**：年龄范围[18, 65]

| 测试点 | 值 | 说明 |
|--------|-----|------|
| 最小值边界 | 18 | 正好等于最小值 |
| 最小值-1 | 17 | 刚好小于最小值 |
| 最小值+1 | 19 | 刚好大于最小值 |
| 最大值边界 | 65 | 正好等于最大值 |
| 最大值-1 | 64 | 刚好小于最大值 |
| 最大值+1 | 66 | 刚好大于最大值 |

### 边界值分析的步骤

1. **识别边界**：找出输入条件的边界值
2. **选择测试值**：选择边界值和边界附近的值
3. **设计测试用例**：为每个边界值设计测试用例
4. **执行测试**：执行测试并验证结果

### 实践示例

#### 示例1：密码长度验证

### 边界值分析的扩展

#### 1. 内部边界值

除了输入域的边界，还要考虑：
- **数组边界**：第一个元素、最后一个元素
- **循环边界**：第一次循环、最后一次循环
- **字符串边界**：空字符串、单字符、最大长度字符串

#### 2. 输出边界值

不仅要测试输入的边界值，还要测试输出的边界值：
- **计算结果边界**：最大值、最小值、零值
- **状态转换边界**：状态转换的临界点

#### 3. 多变量边界值

当有多个输入变量时，需要考虑：
- **每个变量的边界值**
- **变量组合的边界值**（如一个变量取最小值，另一个变量取最大值）

### 边界值分析与等价类划分的结合

边界值分析通常与等价类划分结合使用：

1. **先用等价类划分**：划分输入域
2. **再用边界值分析**：重点测试边界值
3. **补充测试**：测试等价类中的典型值

**示例**：年龄输入[18, 65]

| 方法 | 测试数据 | 说明 |
|------|----------|------|
| 等价类划分 | 25, 30, 45 | 有效等价类的典型值 |
| 边界值分析 | 17, 18, 19, 64, 65, 66 | 边界值和边界附近的值 |
| 组合使用 | 17, 18, 19, 25, 64, 65, 66 | 完整的测试数据集合 |

## 决策表法

### 定义

决策表法（Decision Table）是一种用表格形式表示复杂业务逻辑的测试方法，特别适用于处理多个条件组合的场景。

**核心思想**：
> 将复杂的业务规则用表格形式表示，每个条件组合对应一个测试用例。

### 决策表的组成

决策表由以下部分组成：

1. **条件桩（Condition Stub）**：列出所有输入条件
2. **条件项（Condition Entry）**：列出条件的取值（是/否、真/假等）
3. **动作桩（Action Stub）**：列出所有可能的动作
4. **动作项（Action Entry）**：列出在对应条件组合下应该执行的动作

### 决策表的类型

#### 1. 有限条目决策表

条件项和动作项只有有限个取值（如：是/否、真/假）。

#### 2. 扩展条目决策表

条件项和动作项可以有多个取值（如：高/中/低、VIP/普通/游客）。

### 决策表的设计步骤

1. **识别条件**：找出所有影响结果的条件
2. **识别动作**：找出所有可能的动作或结果
3. **列出条件组合**：列出所有可能的条件组合
4. **确定动作**：为每个条件组合确定对应的动作
5. **简化决策表**：合并相同的动作项，简化表格
6. **设计测试用例**：为每个规则设计测试用例

### 实践示例

#### 示例1：订单折扣规则

**需求**：电商网站的订单折扣规则
- 如果用户是VIP会员，订单金额≥1000元，打9折
- 如果用户是VIP会员，订单金额<1000元，打95折
- 如果用户是普通会员，订单金额≥1000元，使用优惠券时打95折，不使用优惠券不打折
- 如果用户是普通会员，订单金额<1000元，不打折

**条件识别**：
- C1: 会员等级（VIP/普通）
- C2: 订单金额（≥1000/<1000）
- C3: 使用优惠券（是/否）

**动作识别**：
- A1: 打9折
- A2: 打95折
- A3: 不打折

**决策表**：

| 规则 | C1会员等级 | C2订单金额 | C3优惠券 | A1打9折 | A2打95折 | A3不打折 |
|------|-----------|-----------|---------|---------|---------|---------|
| 1 | VIP | ≥1000 | 是 | ✓ | | |
| 2 | VIP | ≥1000 | 否 | ✓ | | |
| 3 | VIP | <1000 | 是 | | ✓ | |
| 4 | VIP | <1000 | 否 | | ✓ | |
| 5 | 普通 | ≥1000 | 是 | | ✓ | |
| 6 | 普通 | ≥1000 | 否 | | | ✓ |
| 7 | 普通 | <1000 | 是 | | | ✓ |
| 8 | 普通 | <1000 | 否 | | | ✓ |

**测试用例**：

| 用例ID | 会员等级 | 订单金额 | 优惠券 | 预期折扣 |
|--------|----------|----------|--------|----------|
| TC_DISC_001 | VIP | 1500 | 是 | 9折 |
| TC_DISC_002 | VIP | 1500 | 否 | 9折 |
| TC_DISC_003 | VIP | 500 | 是 | 95折 |
| TC_DISC_004 | VIP | 500 | 否 | 95折 |
| TC_DISC_005 | 普通 | 1500 | 是 | 95折 |
| TC_DISC_006 | 普通 | 1500 | 否 | 不打折 |
| TC_DISC_007 | 普通 | 500 | 是 | 不打折 |
| TC_DISC_008 | 普通 | 500 | 否 | 不打折 |

#### 示例2：文件上传权限判断

**需求**：文件上传功能需要判断：
- 用户是否有上传权限
- 文件大小是否≤10MB
- 文件类型是否在允许范围内（jpg/png/pdf）

## 因果图法

### 定义

因果图法（Cause-Effect Graph）是一种用图形方式表示输入条件（原因）和输出结果（结果）之间因果关系的测试方法。

**核心思想**：
> 分析输入条件之间的逻辑关系，找出所有可能的输入组合，设计测试用例。

### 因果图的符号

#### 1. 基本符号

- **原因（Cause）**：输入条件，用C表示
- **结果（Effect）**：输出结果，用E表示

#### 2. 逻辑关系符号

- **恒等（Identity）**：原因出现，结果出现
- **非（NOT）**：原因出现，结果不出现；原因不出现，结果出现
- **或（OR）**：多个原因中至少一个出现，结果出现
- **与（AND）**：所有原因都出现，结果才出现

#### 3. 约束符号

- **互斥（E）**：原因不能同时为真
- **包含（I）**：至少有一个原因必须为真
- **唯一（O）**：有且仅有一个原因为真
- **要求（R）**：如果原因1为真，则原因2必须为真
- **屏蔽（M）**：如果结果1为真，则结果2必须为假

### 因果图法的步骤

1. **分析需求**：理解输入条件和输出结果
2. **识别原因和结果**：列出所有原因和结果
3. **绘制因果图**：用图形表示因果关系
4. **标注约束**：标注原因和结果之间的约束
5. **转换为决策表**：将因果图转换为决策表
6. **设计测试用例**：根据决策表设计测试用例

### 实践示例

#### 示例1：文件上传功能

**需求**：文件上传功能
- 如果文件大小≤10MB，文件类型允许，用户有权限，则上传成功
- 如果文件大小>10MB，则提示"文件过大"
- 如果文件类型不允许，则提示"文件类型不支持"
- 如果用户无权限，则提示"无权限"

**原因识别**：
- C1: 文件大小≤10MB
- C2: 文件类型允许
- C3: 用户有权限

**结果识别**：
- E1: 上传成功
- E2: 提示"文件过大"
- E3: 提示"文件类型不支持"
- E4: 提示"无权限"

```

¬C1 → E2
¬C2 → E3

```

| 用例ID | 文件大小 | 文件类型 | 权限 | 预期结果 |
|--------|----------|----------|------|----------|
| TC_CE_001 | 5MB | jpg | 有 | 上传成功 |
| TC_CE_002 | 15MB | jpg | 有 | 提示"文件过大" |
| TC_CE_003 | 5MB | docx | 有 | 提示"文件类型不支持" |

## 正交实验法

### 定义

正交实验法（Orthogonal Array Testing）是一种利用正交表来设计测试用例的方法，可以用最少的测试用例覆盖最多的输入组合。

**核心思想**：
> 使用正交表选择测试用例，在保证测试覆盖的前提下，大幅减少测试用例数量。

### 为什么需要正交实验法？

当有多个输入条件，每个条件有多个取值时，完全组合测试会产生大量的测试用例。

**示例**：3个条件，每个条件3个取值
- 完全组合：3×3×3 = 27个测试用例
- 正交实验法：可能只需要9个测试用例

### 正交表

正交表是一种特殊的表格，具有以下特点：

1. **均匀分散**：每个因素的每个水平在表中出现的次数相同
2. **整齐可比**：任意两个因素的水平组合在表中出现的次数相同

**正交表表示方法**：L<sub>n</sub>(m<sup>k</sup>)
- L：正交表
- n：行数（测试用例数）
- m：水平数（每个因素的取值数）
- k：因素数（输入条件数）

### 常用正交表

| 正交表 | 行数 | 水平数 | 因素数 | 说明 |
|--------|------|--------|--------|------|
| L<sub>4</sub>(2<sup>3</sup>) | 4 | 2 | 3 | 3个因素，每个2个水平 |
| L<sub>8</sub>(2<sup>7</sup>) | 8 | 2 | 7 | 7个因素，每个2个水平 |
| L<sub>9</sub>(3<sup>4</sup>) | 9 | 3 | 4 | 4个因素，每个3个水平 |
| L<sub>16</sub>(4<sup>5</sup>) | 16 | 4 | 5 | 5个因素，每个4个水平 |

### 正交实验法的步骤

1. **识别因素和水平**：确定输入条件和每个条件的取值
2. **选择正交表**：根据因素数和水平数选择合适的正交表
3. **映射到正交表**：将因素和水平映射到正交表
4. **设计测试用例**：根据正交表设计测试用例
5. **补充测试用例**：必要时补充重要的测试用例

### 实践示例

#### 示例1：浏览器兼容性测试

**需求**：测试网站在不同浏览器、操作系统、屏幕分辨率下的兼容性。

**因素和水平**：
- 浏览器：Chrome, Firefox, Safari
- 操作系统：Windows, macOS, Linux
- 屏幕分辨率：1920×1080, 1366×768, 2560×1440

**选择正交表**：L<sub>9</sub>(3<sup>4</sup>)（3个因素，每个3个水平）

**正交表映射**：

| 用例 | 浏览器 | 操作系统 | 分辨率 |
|------|--------|----------|--------|
| 1 | Chrome | Windows | 1920×1080 |
| 2 | Chrome | macOS | 1366×768 |
| 3 | Chrome | Linux | 2560×1440 |
| 4 | Firefox | Windows | 1366×768 |
| 5 | Firefox | macOS | 2560×1440 |
| 6 | Firefox | Linux | 1920×1080 |
| 7 | Safari | Windows | 2560×1440 |
| 8 | Safari | macOS | 1920×1080 |
| 9 | Safari | Linux | 1366×768 |

**优点**：用9个测试用例覆盖了27种组合（3×3×3）

**需求**：测试软件在不同配置下的表现。

**因素和水平**：
- 数据库：MySQL, PostgreSQL, SQLite
- 缓存：Redis, Memcached, 无缓存

### 正交实验法的优缺点

#### 优点

1. **大幅减少测试用例**：用少量用例覆盖大量组合
2. **保证覆盖**：每个因素的每个水平都被测试
3. **系统化**：系统化地选择测试用例

#### 缺点

1. **需要正交表**：需要了解正交表的使用
2. **可能遗漏**：某些重要组合可能不在正交表中
3. **不适合所有场景**：对于因素数或水平数不匹配的情况，需要调整

## 状态转换测试

### 定义

状态转换测试（State Transition Testing）是一种基于状态机的测试方法，适用于测试系统在不同状态之间的转换。

**核心思想**：
> 系统在不同状态下对相同输入可能有不同的响应，需要测试所有可能的状态转换。

### 状态转换图的组成

1. **状态（State）**：系统可能处于的状态
2. **转换（Transition）**：从一个状态转换到另一个状态
3. **事件（Event）**：触发状态转换的输入
4. **动作（Action）**：状态转换时执行的动作

### 状态转换测试的步骤

1. **识别状态**：找出系统可能的所有状态
2. **识别事件**：找出触发状态转换的所有事件
3. **绘制状态转换图**：用图形表示状态和转换
4. **设计测试用例**：测试所有可能的状态转换路径

### 实践示例

- S1: 未激活
- S2: 正常
- S3: 锁定（临时）
- S4: 锁定（永久）

## 错误推测法

### 定义

错误推测法（Error Guessing）是一种基于测试人员经验和直觉的测试方法，通过推测可能出错的地方来设计测试用例。

**核心思想**：
> 基于经验和直觉，推测程序可能出错的地方，设计针对性的测试用例。

### 常见错误类型

#### 1. 输入处理错误

- **空值处理**：输入为空、null、undefined
- **特殊字符**：SQL注入字符、XSS字符、特殊符号
- **数据类型错误**：输入错误的数据类型
- **长度限制**：超长输入、空字符串
- **格式错误**：不符合格式要求的输入

#### 2. 边界值错误

- **数值边界**：最大值、最小值、零值
- **数组边界**：第一个元素、最后一个元素、空数组
- **字符串边界**：空字符串、单字符、最大长度

#### 3. 逻辑错误

- **条件判断错误**：`>`和`>=`混淆
- **循环错误**：无限循环、循环次数错误
- **状态转换错误**：状态转换条件错误

#### 4. 并发错误

- **竞态条件**：多线程/多进程同时访问
- **死锁**：资源竞争导致死锁
- **数据一致性**：并发修改导致数据不一致

#### 5. 权限错误

- **越权访问**：访问未授权的资源
- **权限提升**：普通用户获得管理员权限
- **权限绕过**：绕过权限检查

#### 6. 资源错误

- **内存泄漏**：资源未释放
- **文件操作错误**：文件不存在、权限不足
- **网络错误**：网络中断、超时

### 错误推测法的应用

#### 示例1：用户注册功能

**推测的错误场景**：

| 错误类型 | 测试场景 | 测试数据 |
|---------|---------|---------|
| 空值处理 | 用户名为空 | "" |
| 空值处理 | 密码为空 | "" |
| 特殊字符 | SQL注入 | "admin' OR '1'='1" |
| 特殊字符 | XSS攻击 | "<script>alert('xss')</script>" |
| 长度限制 | 超长用户名 | 1000个字符 |
| 格式错误 | 邮箱格式错误 | "test@" |
| 逻辑错误 | 用户名已存在 | 使用已注册的用户名 |
| 并发错误 | 并发注册相同用户名 | 同时注册相同用户名 |

**推测的错误场景**：

| 文件名 | 特殊字符 | "file<>name.jpg" |
| 文件名 | 超长文件名 | 500个字符的文件名 |
| 并发错误 | 同时上传相同文件 | 多用户同时上传 |
| 资源错误 | 磁盘空间不足 | 在磁盘满时上传 |

### 错误推测法的优缺点

#### 优点

1. **针对性强**：针对常见错误设计测试用例
2. **效率高**：快速发现常见缺陷
3. **经验积累**：随着经验积累，推测能力增强

#### 缺点

1. **依赖经验**：需要测试人员有丰富的经验
2. **不系统**：可能遗漏某些错误
3. **主观性强**：不同人员的推测可能不同

### 提高错误推测能力的方法

1. **积累经验**：记录和分析发现的缺陷
2. **学习常见错误**：了解常见错误类型和模式
3. **代码审查**：通过代码审查了解可能的错误
4. **缺陷分析**：分析历史缺陷，找出规律
5. **团队讨论**：与团队讨论可能的错误场景

## 黑盒测试方法对比与选择

### 方法对比

| 方法 | 适用场景 | 优点 | 缺点 | 测试用例数量 |
|------|---------|------|------|-------------|
| 等价类划分 | 输入有明确范围 | 系统化，覆盖完整 | 可能遗漏边界值 | 中等 |
| 边界值分析 | 输入有边界 | 发现边界错误 | 只关注边界 | 较少 |
| 决策表法 | 复杂业务规则 | 逻辑清晰，覆盖完整 | 组合爆炸 | 较多 |
| 因果图法 | 条件有依赖关系 | 系统化分析 | 设计复杂 | 中等 |
| 正交实验法 | 多因素多水平 | 大幅减少用例数 | 需要正交表 | 较少 |
| 状态转换测试 | 有状态转换 | 覆盖状态转换 | 状态识别困难 | 中等 |
| 错误推测法 | 所有场景 | 针对性强 | 依赖经验 | 不定 |

### 方法选择原则

1. **根据输入特点选择**
   - 输入有明确范围：等价类划分 + 边界值分析
   - 输入有多个条件：决策表法或因果图法
   - 输入有多个因素：正交实验法

2. **根据系统特点选择**
   - 有状态转换：状态转换测试
   - 复杂业务规则：决策表法
   - 条件有依赖：因果图法

3. **组合使用**
   - 通常组合使用多种方法
   - 先用等价类划分，再用边界值分析
   - 用错误推测法补充测试用例

### 综合应用示例

**场景**：用户注册功能测试

**输入条件**：
- 用户名：6-20个字符，字母数字下划线
- 密码：8-16个字符，必须包含大小写字母和数字
- 邮箱：符合邮箱格式
- 验证码：4位数字

**方法组合**：

1. **等价类划分**：划分用户名、密码、邮箱的有效和无效等价类
2. **边界值分析**：测试用户名长度6、20、5、21；密码长度8、16、7、17
3. **决策表法**：处理多个条件的组合（如用户名有效+密码无效+邮箱有效）
4. **错误推测法**：SQL注入、XSS攻击、并发注册等

**测试用例设计**：

| 方法 | 测试用例数 | 说明 |
|------|-----------|------|
| 等价类划分 | 15个 | 覆盖各种等价类 |
| 边界值分析 | 10个 | 覆盖边界值 |
| 决策表法 | 8个 | 覆盖条件组合 |
| 错误推测法 | 5个 | 覆盖常见错误 |
| **总计** | **38个** | 去除重复后约30个 |

## 实践案例

### 案例1：电商购物车功能测试

**需求**：电商网站的购物车功能
- 用户可以添加商品到购物车
- 可以修改商品数量（1-99）
- 可以删除商品
- 自动计算总价
- 库存不足时不能添加

**测试方法组合**：

1. **等价类划分**：
   - 商品数量：有效（1-99）、无效（<1, >99, 非数字）
   - 库存：充足、不足、为0

2. **边界值分析**：
   - 数量：1, 99, 0, 100
   - 库存：1, 0

3. **状态转换测试**：
   - 空购物车 → 有商品 → 空购物车
   - 商品数量变化的状态

4. **错误推测法**：
   - 并发添加相同商品
   - 商品下架后操作购物车
   - 价格变化时的处理

**测试用例示例**：

| 用例ID | 测试场景 | 商品数量 | 库存 | 预期结果 |
|--------|----------|----------|------|----------|
| TC_CART_001 | 正常添加 | 1 | 充足 | 添加成功 |
| TC_CART_002 | 边界值最小 | 1 | 充足 | 添加成功 |
| TC_CART_003 | 边界值最大 | 99 | 充足 | 添加成功 |
| TC_CART_004 | 超过最大值 | 100 | 充足 | 拒绝，提示"数量不能超过99" |
| TC_CART_005 | 数量为0 | 0 | 充足 | 拒绝，提示"数量至少为1" |
| TC_CART_006 | 库存不足 | 5 | 3 | 拒绝，提示"库存不足" |
| TC_CART_007 | 库存为0 | 1 | 0 | 拒绝，提示"商品已售罄" |

### 案例2：在线支付功能测试

**需求**：在线支付功能
- 支持多种支付方式（支付宝、微信、银行卡）
- 支付金额范围：1-50000元
- 需要验证支付密码
- 支付超时：15分钟

**测试方法组合**：

1. **等价类划分**：
   - 支付方式：支付宝、微信、银行卡、其他
   - 支付金额：有效（1-50000）、无效（<1, >50000）
   - 支付密码：正确、错误、为空

2. **边界值分析**：
   - 金额：1, 50000, 0, 50001
   - 超时：14分59秒, 15分, 15分01秒

3. **决策表法**：
   - 支付方式 × 支付金额 × 支付密码的组合

4. **状态转换测试**：
   - 待支付 → 支付中 → 支付成功/失败
   - 支付超时的状态转换

**测试用例示例**：

| 用例ID | 支付方式 | 金额 | 密码 | 预期结果 |

| TC_PAY_002 | 支付宝 | 1 | 正确 | 支付成功 |
| TC_PAY_003 | 支付宝 | 50000 | 正确 | 支付成功 |
| TC_PAY_004 | 支付宝 | 0 | 正确 | 拒绝，提示"金额至少1元" |
| TC_PAY_005 | 支付宝 | 50001 | 正确 | 拒绝，提示"金额不能超过50000元" |
| TC_PAY_006 | 支付宝 | 100 | 错误 | 拒绝，提示"密码错误" |

## 练习题

### 思考题

1. 黑盒测试和白盒测试的主要区别是什么？各适用于什么场景？
2. 等价类划分法中，如何区分有效等价类和无效等价类？
3. 边界值分析法为什么重要？如何选择边界值？
4. 决策表法适用于什么场景？如何简化决策表？
5. 因果图法和决策表法有什么关系？如何将因果图转换为决策表？
6. 正交实验法如何减少测试用例数量？什么情况下使用正交实验法？
7. 状态转换测试适用于什么类型的系统？如何识别系统的状态？
8. 错误推测法如何提高测试效果？如何积累错误推测的经验？

### 实践题

1. **设计登录功能测试用例**
   - 使用等价类划分和边界值分析
   - 输入：用户名（6-20字符）、密码（8-16字符）、验证码（4位数字）
   - 设计至少20个测试用例

2. **设计订单折扣功能测试用例**
   - 使用决策表法
   - 条件：会员等级（VIP/普通）、订单金额（≥1000/<1000）、使用优惠券（是/否）
   - 设计完整的决策表和测试用例

3. **设计文件上传功能测试用例**
   - 使用因果图法
   - 条件：文件大小（≤10MB）、文件类型（jpg/png/pdf）、用户权限（有/无）
   - 绘制因果图并设计测试用例

4. **设计浏览器兼容性测试用例**
   - 使用正交实验法
   - 因素：浏览器（Chrome/Firefox/Safari）、操作系统（Windows/macOS/Linux）、分辨率（1920×1080/1366×768）
   - 选择合适的正交表并设计测试用例

5. **设计用户账号状态转换测试用例**
   - 使用状态转换测试
   - 状态：未激活、正常、锁定、永久锁定
   - 绘制状态转换图并设计测试用例

6. **综合应用多种方法**
   - 选择一个实际功能（如商品搜索、用户注册等）
   - 综合应用等价类划分、边界值分析、决策表法、错误推测法
   - 设计完整的测试用例集
