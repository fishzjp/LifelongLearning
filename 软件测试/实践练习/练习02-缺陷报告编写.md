并发购买最后一件商品导致库存为负，订单数据不一致

## 环境信息

- **测试环境**：测试环境 v2.3.1
- **数据库**：MySQL 8.0
- **缓存**：Redis 6.2
- **并发工具**：JMeter 5.5

## 问题描述

当多个用户同时购买最后一件商品时，系统允许所有用户购买成功，导致：
1. 库存变为负数
2. 产生多个订单
3. 资金扣减正确但商品超卖

## 复现步骤

**准备数据**：
- 商品ID: PROD-001
- 当前库存: 1
- 商品价格: 100元

**并发测试**：
1. 使用JMeter创建2个线程组
2. 线程组1（用户A）：下单商品PROD-001
3. 线程组2（用户B）：下单商品PROD-001
4. 设置两个线程组同时启动（0秒延迟）
5. 执行测试

**时序分析**：
```
时间线：
T0: 用户A查询库存，库存=1
T1: 用户B查询库存，库存=1
T2: 用户A扣减库存，库存=0
T3: 用户B扣减库存，库存=-1  ❌ 问题点
T4: 用户A创建订单成功
T5: 用户B创建订单成功
```

## 实际结果

1. 用户A订单：ORDER-20240116001，金额100元，状态已支付
2. 用户B订单：ORDER-20240116002，金额100元，状态已支付
3. 商品库存：-1
4. 数据库记录：
   - order表：2条记录
   - inventory表：quantity = -1
   - transaction表：2条扣款记录

## 期望结果

1. 只有一个用户购买成功
2. 另一个用户提示"库存不足"
3. 库存最终为0
4. 只产生一个订单

## 严重程度说明

**严重 (Critical)**：
- 数据一致性严重破坏
- 导致超卖，影响商家利益
- 可能引发用户投诉和纠纷
- 影响平台信誉

## 优先级说明

**紧急 (P0)**：
- 数据严重错误
- 涉及资金和库存
- 需要立即修复
- 有业务风险

## 根因分析

**技术原因**：
1. 库存扣减未使用分布式锁
2. 数据库事务隔离级别不够（默认Read Committed）
3. 缺少库存预扣机制
4. 未使用数据库乐观锁或悲观锁

**代码位置**：
- src/services/OrderService.java:156
- src/services/InventoryService.java:89

## 解决方案建议
### 短期方案（立即实施）

1. 库存扣减使用数据库悲观锁（SELECT FOR UPDATE）
2. 添加分布式锁（Redis）
3. 库存校验和扣减在同一事务中

### 长期方案

1. 实现库存预扣机制
2. 使用消息队列处理订单
3. 引入库存流水表
4. 添加库存预警机制

## 影响范围

- **用户影响**：所有抢购场景
- **业务影响**：秒杀、限时抢购、库存紧张商品
- **数据影响**：库存数据、订单数据
- **时间影响**：从上线至今（2024-01-14至今）

### 1. 标题编写

**好的标题**：
- "购物车结算按钮点击后页面白屏"
- "并发购买导致库存为负"
- "商品详情页加载时间超过5秒"

**差的标题**：
- "页面有问题"
- "功能不能用"
- "性能很差"

### 2. 步骤编写原则

- **原子性**：每一步只做一件事
- **顺序性**：按实际操作顺序
- **完整性**：包含所有必要操作
- **可复现**：其他人能按步骤复现

### 3. 环境信息

- 操作系统及版本
- 浏览器及版本
- 设备型号
- 网络环境
- 测试环境版本
- 测试账号

### 4. 附件规范

- 截图要清晰，标注关键信息
- 日志要完整，脱敏敏感信息
- 视频要简短，展示关键操作
- 数据要准确，提供SQL或JSON

### 🌳 缺陷分级决策树

```bash
# 缺陷分级决策树

## 严重程度判断

### 致命 (Critical) - P0

```
是否导致系统崩溃？
├─ 是 → 致命
└─ 否 → 继续判断
   是否导致数据丢失/损坏？
   ├─ 是 → 致命
   └─ 否 → 继续判断
      是否影响核心业务流程？
      ├─ 是 → 致命
      └─ 否 → 严重
```

### 严重 (Major) - P1

```
是否影响主要功能？
├─ 是 → 严重
└─ 否 → 继续判断
   是否影响用户体验？
   ├─ 是 → 严重
   └─ 否 → 一般
```

### 一般 (Minor) - P2

```
是否影响功能使用？
├─ 是 → 一般
└─ 否 → 轻微
```

### 轻微 (Trivial) - P3

```
UI小问题/文案错误
└─ 轻微
```

## 优先级判断

### 紧急 (P0)

- 影响生产环境
- 导致用户投诉
- 涉及资金安全

### 高 (P1)

- 阻塞测试进度
- 影响版本发布
- 核心功能问题

### 中 (P2)

- 影响非核心功能
- 有临时解决方案
- 可以延期修复

### 低 (P3)

- 优化建议
- 边缘场景
- 低频使用
```

## 🎓 缺陷分析技巧

### 1. 根因分析方法

```
5 Whys分析法：
问题：购物车结算白屏
├─ Why1：为什么白屏？→ 接口超时
├─ Why2：为什么超时？→ 数据库查询慢
├─ Why3：为什么慢？→ 缺少索引
├─ Why4：为什么没索引？→ 需求变更未更新
└─ Why5：为什么没更新？→ 缺少变更评审流程
```

### 2. 缺陷趋势分析

```
统计维度：
- 按模块：哪个模块缺陷最多？
- 按类型：功能/性能/安全占比？
- 按严重程度：高危缺陷比例？
- 按时间：缺陷趋势如何？
```

### 3. 缺陷预防

```
预防措施：
├─ 需求阶段：明确验收标准
├─ 设计阶段：技术方案评审
├─ 开发阶段：代码审查、单元测试
├─ 测试阶段：充分测试、回归测试
└─ 上线阶段：灰度发布、监控告警
```
