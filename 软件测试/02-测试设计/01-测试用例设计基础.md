## 什么是测试用例

### 定义

测试用例（Test Case）是一组条件或变量，测试人员根据它来确定应用程序或软件系统是否正常工作。

**IEEE 610.12标准定义**：
> 测试用例是一组输入值、执行条件、预期结果和测试后置条件，用于测试特定程序路径或验证是否符合特定需求。

### 测试用例的作用

1. **指导测试执行**
   - 明确测试步骤
   - 统一测试标准
   - 提高测试效率

2. **保证测试覆盖**
   - 确保需求被完整测试
   - 避免遗漏测试场景
   - 提供测试依据

3. **便于测试管理**
   - 跟踪测试进度
   - 评估测试质量
   - 支持测试报告

4. **知识沉淀**
   - 记录测试经验
   - 便于新人学习
   - 支持回归测试

## 测试用例的组成

### 基本要素

一个完整的测试用例应包含以下要素：

#### 1. 测试用例标识（Test Case ID）

**作用**：唯一标识测试用例

**命名规则**：
- 项目缩写_模块_功能_序号
- 示例：TC_LOGIN_001, TC_ORDER_CREATE_001

#### 2. 测试用例名称（Test Case Name）

**要求**：
- 简洁明了
- 描述测试目的
- 易于理解

**示例**：
- ✅ "验证有效用户名和密码的登录功能"
- ❌ "测试登录"

#### 3. 测试目标（Test Objective）

**说明**：测试用例的目的和验证点

**示例**：
- 验证用户可以使用有效凭据成功登录系统
- 验证系统拒绝无效的登录尝试

#### 4. 前置条件（Preconditions）

**说明**：执行测试用例前必须满足的条件

**示例**：
- 用户已注册，账号状态正常
- 系统已启动并运行正常
- 测试数据已准备

#### 5. 测试步骤（Test Steps）

**要求**：
- 步骤清晰、可执行
- 按顺序编号
- 每个步骤一个操作

**格式**：
```
步骤1: 打开登录页面
步骤2: 输入用户名"testuser"
步骤3: 输入密码"Test123456"
步骤4: 点击"登录"按钮
```

#### 6. 测试数据（Test Data）

**说明**：测试用例使用的输入数据

**示例**：
- 用户名：testuser
- 密码：Test123456
- 验证码：1234

#### 7. 预期结果（Expected Result）

**要求**：
- 明确、可验证
- 与测试目标一致
- 包含多个验证点

**示例**：
- 成功登录，跳转到首页
- 显示用户名"testuser"
- URL变为"/home"

#### 8. 实际结果（Actual Result）

**说明**：测试执行后的实际结果（执行时填写）

#### 9. 测试状态（Test Status）

**可能值**：
- 通过（Pass）
- 失败（Fail）
- 阻塞（Blocked）
- 未执行（Not Executed）

#### 10. 优先级（Priority）

**级别**：
- P1 - 高优先级（核心功能）
- P2 - 中优先级（重要功能）
- P3 - 低优先级（次要功能）

#### 11. 测试类型（Test Type）

**类型**：
- 功能测试
- 性能测试
- 安全测试
- 兼容性测试

#### 12. 所属模块（Module）

**说明**：测试用例所属的功能模块

### 完整测试用例示例

```yaml
测试用例ID: TC_LOGIN_001
测试用例名称: 验证有效用户名和密码的登录功能
测试目标: 验证用户可以使用有效凭据成功登录系统
所属模块: 用户登录模块
测试类型: 功能测试
优先级: P1

前置条件:
1. 用户已注册，用户名"testuser"，密码"Test123456"
2. 用户账号状态正常，未被锁定
3. 系统已启动并运行正常
4. 浏览器已打开

测试数据:
- 用户名: testuser
- 密码: Test123456
- 验证码: 1234（如果启用）

测试步骤:
1. 打开浏览器，访问登录页面（http://example.com/login）
2. 在"用户名"输入框中输入"testuser"
3. 在"密码"输入框中输入"Test123456"
4. 如果显示验证码，输入验证码"1234"
5. 点击"登录"按钮

预期结果:
1. 登录成功，页面跳转到首页（http://example.com/home）
2. 页面右上角显示用户名"testuser"
3. 显示"登录成功"提示信息（如果有）
4. 用户会话已建立，可以访问需要登录的功能

实际结果: （执行时填写）
测试状态: 未执行
执行人: 
执行日期: 
备注: 
```

## 测试用例编写规范

### 编写原则

#### 1. 清晰性原则

- 使用简洁明了的语言
- 避免歧义
- 步骤具体可执行

**示例**：
- ✅ "在用户名输入框输入'testuser'"
- ❌ "输入用户名"

#### 2. 完整性原则

- 包含所有必要信息
- 覆盖前置条件、步骤、预期结果
- 考虑异常情况

#### 3. 可重复性原则

- 任何人在任何时间执行都能得到相同结果
- 不依赖特定环境或数据
- 步骤明确，不依赖个人经验

#### 4. 独立性原则

- 每个测试用例独立
- 不依赖其他测试用例的执行结果
- 可以单独执行

#### 5. 可维护性原则

- 使用统一的模板
- 命名规范一致
- 便于更新和维护

### 编写技巧

#### 1. 使用动作词

**好的动作词**：
- 打开、点击、输入、选择、验证、检查

**示例**：
```
步骤1: 打开登录页面
步骤2: 输入用户名"testuser"
步骤3: 点击"登录"按钮
步骤4: 验证页面跳转到首页
```

#### 2. 一个步骤一个操作

**正确**：
```
步骤1: 打开登录页面
步骤2: 输入用户名"testuser"
步骤3: 输入密码"Test123456"
步骤4: 点击"登录"按钮
```

**错误**：
```
步骤1: 打开登录页面，输入用户名和密码，点击登录按钮
```

#### 3. 明确验证点

**好的验证**：
```
预期结果:
1. 页面跳转到首页
2. URL变为"/home"
3. 显示用户名"testuser"
4. 可以访问需要登录的功能
```

**不好的验证**：
```
预期结果: 登录成功
```

#### 4. 使用测试数据表

对于需要多组数据测试的场景，使用数据表：

| 用例ID | 用户名 | 密码 | 预期结果 |
|--------|--------|------|----------|
| TC_LOGIN_001 | testuser | Test123456 | 登录成功 |
| TC_LOGIN_002 | wronguser | Test123456 | 登录失败 |
| TC_LOGIN_003 | testuser | wrongpass | 登录失败 |
| TC_LOGIN_004 | (空) | Test123456 | 提示输入用户名 |

## 测试用例设计方法

### 1. 等价类划分法（Equivalence Partitioning）

**原理**：将所有可能的输入数据分成若干等价类，从每个等价类中选择代表性数据进行测试。

**步骤**：
1. 划分有效等价类和无效等价类
2. 为每个等价类设计测试用例
3. 选择边界值作为补充

**示例**：用户年龄输入（要求18-65岁）

**等价类划分**：
- 有效等价类：18-65之间的整数
- 无效等价类1：小于18的整数
- 无效等价类2：大于65的整数
- 无效等价类3：非数字字符
- 无效等价类4：空值

**测试用例**：

| 用例ID | 输入年龄 | 等价类 | 预期结果 |
|--------|----------|--------|----------|
| TC_AGE_001 | 25 | 有效等价类 | 接受 |
| TC_AGE_002 | 18 | 边界值 | 接受 |
| TC_AGE_003 | 65 | 边界值 | 接受 |
| TC_AGE_004 | 17 | 无效等价类1 | 拒绝，提示年龄不足 |
| TC_AGE_005 | 66 | 无效等价类2 | 拒绝，提示年龄超限 |
| TC_AGE_006 | abc | 无效等价类3 | 拒绝，提示输入数字 |
| TC_AGE_007 | (空) | 无效等价类4 | 拒绝，提示必填 |

### 2. 边界值分析法（Boundary Value Analysis）

**原理**：测试边界值和边界附近的值，因为缺陷往往出现在边界处。

**边界值选择**：
- 正好等于边界值
- 刚好大于边界值
- 刚好小于边界值

**示例**：密码长度（要求6-20个字符）

**边界值**：
- 最小值：6
- 最大值：20
- 边界附近：5, 7, 19, 21

**测试用例**：

| 用例ID | 密码长度 | 密码值 | 预期结果 |
|--------|----------|--------|----------|
| TC_PWD_001 | 6 | "123456" | 接受 |
| TC_PWD_002 | 5 | "12345" | 拒绝，提示至少6个字符 |
| TC_PWD_003 | 7 | "1234567" | 接受 |
| TC_PWD_004 | 20 | "12345678901234567890" | 接受 |
| TC_PWD_005 | 21 | "123456789012345678901" | 拒绝，提示最多20个字符 |
| TC_PWD_006 | 19 | "1234567890123456789" | 接受 |

### 3. 决策表法（Decision Table）

**原理**：用表格表示条件组合和对应的动作，适合复杂的业务规则。

**步骤**：
1. 列出所有条件
2. 列出所有动作
3. 列出条件的所有组合
4. 为每个组合设计测试用例

**示例**：订单折扣规则

**条件**：
- C1: 会员等级（VIP/普通）
- C2: 订单金额（≥1000/<1000）
- C3: 使用优惠券（是/否）

**动作**：
- A1: 打9折
- A2: 打95折
- A3: 不打折

**决策表**：

| 规则 | C1 | C2 | C3 | A1 | A2 | A3 |
|------|----|----|----|----|----|----|
| 1 | VIP | ≥1000 | 是 | ✓ | | |
| 2 | VIP | ≥1000 | 否 | ✓ | | |
| 3 | VIP | <1000 | 是 | | ✓ | |
| 4 | VIP | <1000 | 否 | | ✓ | |
| 5 | 普通 | ≥1000 | 是 | | ✓ | |
| 6 | 普通 | ≥1000 | 否 | | | ✓ |
| 7 | 普通 | <1000 | 是 | | | ✓ |
| 8 | 普通 | <1000 | 否 | | | ✓ |

**测试用例**：

| 用例ID | 会员等级 | 订单金额 | 优惠券 | 预期折扣 |
|--------|----------|----------|--------|----------|
| TC_DISC_001 | VIP | 1500 | 是 | 9折 |
| TC_DISC_002 | VIP | 1500 | 否 | 9折 |
| TC_DISC_003 | VIP | 500 | 是 | 95折 |
| TC_DISC_004 | VIP | 500 | 否 | 95折 |
| TC_DISC_005 | 普通 | 1500 | 是 | 95折 |
| TC_DISC_006 | 普通 | 1500 | 否 | 不打折 |
| TC_DISC_007 | 普通 | 500 | 是 | 不打折 |
| TC_DISC_008 | 普通 | 500 | 否 | 不打折 |

### 4. 因果图法（Cause-Effect Graph）

**原理**：分析输入条件之间的因果关系，设计测试用例。

**适用场景**：条件之间有依赖关系

**示例**：文件上传功能

**原因（输入条件）**：
- C1: 文件大小 ≤ 10MB
- C2: 文件类型为允许类型
- C3: 用户有上传权限

**结果（输出）**：
- E1: 上传成功
- E2: 显示错误提示

**因果图**：
```
C1 ∧ C2 ∧ C3 → E1
¬C1 ∨ ¬C2 ∨ ¬C3 → E2
```

**测试用例**：

| 用例ID | C1 | C2 | C3 | 预期结果 |
|--------|----|----|----|----------|
| TC_UPLOAD_001 | ✓ | ✓ | ✓ | E1: 上传成功 |
| TC_UPLOAD_002 | ✗ | ✓ | ✓ | E2: 文件过大 |
| TC_UPLOAD_003 | ✓ | ✗ | ✓ | E2: 文件类型不支持 |
| TC_UPLOAD_004 | ✓ | ✓ | ✗ | E2: 无权限 |

### 5. 正交实验法（Orthogonal Array）

**原理**：使用正交表选择测试用例，用最少的用例覆盖最多的组合。

**适用场景**：多因素多水平的测试

**示例**：浏览器兼容性测试

**因素和水平**：
- 浏览器：Chrome, Firefox, Safari
- 操作系统：Windows, macOS, Linux
- 屏幕分辨率：1920x1080, 1366x768, 2560x1440

**正交表 L9(3^3)**：

| 用例 | 浏览器 | 操作系统 | 分辨率 |
|------|--------|----------|--------|
| 1 | Chrome | Windows | 1920x1080 |
| 2 | Chrome | macOS | 1366x768 |
| 3 | Chrome | Linux | 2560x1440 |
| 4 | Firefox | Windows | 1366x768 |
| 5 | Firefox | macOS | 2560x1440 |
| 6 | Firefox | Linux | 1920x1080 |
| 7 | Safari | Windows | 2560x1440 |
| 8 | Safari | macOS | 1920x1080 |
| 9 | Safari | Linux | 1366x768 |

**优点**：用9个用例覆盖27种组合（3×3×3）

### 6. 错误推测法（Error Guessing）

**原理**：基于经验和直觉，推测可能出错的地方。

**常见错误类型**：
- 空值处理
- 特殊字符处理
- 数据类型错误
- 边界值错误
- 并发问题
- 权限问题

**示例**：用户注册功能

**推测的错误场景**：
1. 用户名为空
2. 密码为空
3. 邮箱格式错误
4. 用户名已存在
5. 密码强度不足
6. 特殊字符处理（如SQL注入）
7. 超长输入
8. 并发注册相同用户名

## 测试用例优先级

### 优先级划分

#### P1 - 高优先级（Critical）

**特点**：
- 核心功能
- 影响主要业务流程
- 必须测试

**示例**：
- 用户登录功能
- 支付功能
- 订单创建功能

#### P2 - 中优先级（High）

**特点**：
- 重要功能
- 影响部分用户
- 应该测试

**示例**：
- 商品搜索功能
- 购物车功能
- 用户资料修改

#### P3 - 低优先级（Medium）

**特点**：
- 次要功能
- 影响少数用户
- 有时间再测试

**示例**：
- 帮助文档
- 界面美化
- 非关键功能

### 优先级确定原则

1. **业务重要性**：核心业务功能优先级高
2. **用户影响**：影响用户多的功能优先级高
3. **风险程度**：风险高的功能优先级高
4. **使用频率**：使用频率高的功能优先级高

## 实践案例

### 案例：用户注册功能测试用例设计

#### 需求分析

**功能描述**：用户可以通过邮箱注册账号

**输入字段**：
- 邮箱：必填，格式验证
- 密码：必填，6-20个字符，必须包含字母和数字
- 确认密码：必填，必须与密码一致
- 验证码：必填，4位数字

**业务规则**：
- 邮箱不能重复注册
- 密码强度验证
- 验证码正确性验证

#### 测试用例设计

**使用等价类划分和边界值分析**：

| 用例ID | 测试场景 | 邮箱 | 密码 | 确认密码 | 验证码 | 预期结果 |
|--------|----------|------|------|----------|--------|----------|
| TC_REG_001 | 正常注册 | test@example.com | Test123456 | Test123456 | 1234 | 注册成功 |
| TC_REG_002 | 邮箱为空 | (空) | Test123456 | Test123456 | 1234 | 提示输入邮箱 |
| TC_REG_003 | 邮箱格式错误 | test@ | Test123456 | Test123456 | 1234 | 提示邮箱格式错误 |
| TC_REG_004 | 邮箱已存在 | exist@example.com | Test123456 | Test123456 | 1234 | 提示邮箱已注册 |
| TC_REG_005 | 密码为空 | test@example.com | (空) | Test123456 | 1234 | 提示输入密码 |
| TC_REG_006 | 密码长度不足 | test@example.com | Test1 | Test1 | 1234 | 提示密码至少6个字符 |
| TC_REG_007 | 密码长度边界值6 | test@example.com | Test12 | Test12 | 1234 | 接受 |
| TC_REG_008 | 密码长度边界值20 | test@example.com | Test1234567890123456 | Test1234567890123456 | 1234 | 接受 |
| TC_REG_009 | 密码长度超限 | test@example.com | Test12345678901234567 | Test12345678901234567 | 1234 | 提示密码最多20个字符 |
| TC_REG_010 | 密码无字母 | test@example.com | 12345678 | 12345678 | 1234 | 提示密码必须包含字母 |
| TC_REG_011 | 密码无数字 | test@example.com | TestTest | TestTest | 1234 | 提示密码必须包含数字 |

## 练习题

### 思考题

1. 测试用例应该包含哪些基本要素？每个要素的作用是什么？
2. 等价类划分法的原理是什么？如何划分等价类？
3. 边界值分析法为什么重要？如何选择边界值？
4. 决策表法适用于什么场景？如何设计决策表？
5. 如何确定测试用例的优先级？

### 实践题

1. **设计登录功能测试用例**
   - 使用等价类划分和边界值分析
   - 设计至少15个测试用例
   - 包含正常情况、异常情况、边界情况

2. **设计搜索功能测试用例**
   - 搜索条件：关键词（1-50字符）、分类、价格范围
   - 使用决策表法设计测试用例
   - 考虑各种条件组合

3. **设计文件上传功能测试用例**
   - 条件：文件大小（≤10MB）、文件类型（jpg/png/pdf）、用户权限
   - 使用因果图法设计测试用例
   - 考虑条件之间的依赖关系

4. **优化测试用例**
   - 选择一个现有测试用例
   - 检查是否符合编写规范
   - 优化使其更清晰、完整、可维护
